# Slice02 persistence compatibility proof

Status: CC-proposed evidence; CDC replay/review and DEP2-02 acceptance remain open. All baseline fixtures are synthetic, immutable originals produced by product APIs under the accepted slice01 lock. Reader and rebuild operations use owned copies. The SHA-256 fixture manifest is `baseline-fixtures/sha256-manifest.json`; all 27 original files were independently rehashed after the iteration03 read/rebuild checks and matched.

## Redb checkpoint and hashes

- Baseline writer: `probes/redb_old_writer.rs`, executed with the source-pinned Redb 4.0.0 workspace using the product `RedbStateStore::open`, `save_checkpoint` and `save_completed_hashes`. It writes the actual `checkpoints: &str -> &[u8]`, `hashes: &str -> &str`, and `metadata: &str -> &str` tables, then closes the writer. The golden checkpoint is run `cc-fixture-run-42`, with authored timestamp, schedule, spec, stage/item state, hash and statistics, plus two completed-hash records.
- Upgraded reader: `probes/redb_new_reader.rs`. `redb-iter02-whole-state01.log` records a direct Redb 5 read of the raw checkpoint bytes and metadata pointers, closure of those handles before opening the product reader, semantic equality of the complete deserialized checkpoint JSON against the independent raw JSON value, and exact equality of both hashes. The actual probe reported one checkpoint and 1705 raw JSON bytes. The original file was not opened concurrently across Redb versions and was not modified.
- Current product save/load/reopen coverage remains in the vector of existing `redb_store` tests and the full debug/release workspace suites. The old fixture reader comparison is not a migration layer; no speculative file conversion was added.

## Lance/vector rows, schema and metadata

- Baseline writer: `probes/lance_old_writer.rs`, executed against the pinned slice01 Cargo.lock: lancedb 0.27.2, Lance 4.0.0 and Arrow 57.3.0. It uses `LancedbBackend::build` and product `persistence::save_metadata`. Three named documents have authored 4D zero/one/two vectors, nullable and non-null category examples, complete metadata maps, and fixed `IndexMetadata`. The synthetic query embedding provider supplies test input only; storage/query use the actual Lance backend.
- Full old-table SDK reader: `probes/lance_new_reader.rs`; successful fresh-copy replay is `lance-new-reader-iteration03-pass01.log`. It asserts exactly three unique rows; every id, text, category, metadata map and vector; complete field order/types/nullability; and the dimension-four `FixedSizeList<Float32>` child named `item`, nullable. Product metadata JSON and freshness are also compared with the authored golden value.
- Product rebuild/query replay: `probes/lance_rebuild_query.rs`; `lance-rebuild-query-iteration03-pass01.log`. On another old-fixture copy, it verifies squared L2 distances 0/4/16 and scores 1/0.2/1/17 in returned ranking, category/threshold behavior, exact metadata conjunction, farther-only owner match at limit one, absent-key empty results, rebuilt contents and preservation of an unrelated table created for this replay. No baseline filtered-query behavior is claimed: the old writer did not execute such a query. The current backend has no open-existing constructor; no public restore API was added.
- Bounded current filter path: `test-vector-iteration03-limit02.log` is the final post-fix product test witness (Rust 1.100.0, 15 passed, Cargo status 0). The nonempty-table absent-key predicate with `usize::MAX` returns empty without capacity panic; zero limit remains empty; a 260-row fixture crosses multiple 128-row scan batches and a limit of 300 returns all 260 matches, including a late winner, with native distance/score/order assertions. Physical plans show the metadata-only `_rowid` scan and numeric native row-id restriction before Lance `KNNVectorDistance(l2)` and `TopK(fetch=1)`. Storage filtering reads O(N) metadata and can issue `ceil(M/128)` vector queries for M matching IDs; this latency cost is stated without a benchmark or fused-filter performance claim.

## Tantivy stored index

- Baseline writer: `probes/tantivy_old_writer.rs`, actual Tantivy 0.26.0 product `Indexer::new/add_document/commit`, with authored text, description, category and stored metadata for three records. Writer shutdown precedes reader use.
- Upgraded product reader: `probes/tantivy_new_reader.rs`; `tantivy-iteration03-all-records01.log` records successful replay on a fresh copy using Tantivy 0.27.0 and the actual `TantivySearch::new/search` APIs. All three IDs occur exactly once. The probe checks all fields exposed by `SearchResult`, finite positive relevance, total/count, category and stemming. Snippets reflect the literal query matcher and the authored old-writer description/content controls; no exact cross-version BM25 value is asserted. Stored tags/author/date/part are not claimed as product-returned fields. No old index rewrite occurred.

## Unchanged/current boundaries

Current Lance and Redb save/load/reopen tests, Tantivy roundtrips, and the real Lance native-distance regression remain part of the latest-stable debug/release workspace test evidence. The graph-rkyv-cache module exposes hashing, not an archive persistence API; the existing graph JSON persistence surface was not misrepresented as an rkyv fixture.
