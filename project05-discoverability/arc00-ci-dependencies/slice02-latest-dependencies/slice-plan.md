### Lance metadata filtering

Actual exposed contract: LancedbBackend owns a private connection/table/count, has only build (explicit table overwrite) and VectorBackend::search; no open-existing constructor or public index mutation API. SearchParams supports arbitrary string-map conjunction, category, limit and threshold; results retain native squared-L2 distance and1/(1+distance) scores sorted descending. Current build creates a table, not an ANN index, despite general documentation calling the backend approximate search. Do not add an index/restore feature in this arc.

The working all-N vector query plus try_collect buffers every candidate's complete row, including text/vector, for metadata predicates. This is **unaccepted**. Merely setting an output batch size or retaining top-k after collecting does not bound the native top-N query. Both lance-datafusion4.0.0/src/udf/json.rs241–248 and14.0.2 corresponding229–236 require JSONB LargeBinary, while persisted metadata is Utf8 JSON. No baseline filtered search was executed; no new14-regression claim is supported.

Source-backed alternatives assessed:

- Stream an all-N vector result and keep top-k: reduces caller buffering but still asks native KNN for N candidates; does not establish bounded total query memory. Reject as a sufficient fix.
- Native JSONB auxiliary column/new metadata schema or private DataFusion JSON-parsing UDF: can support fused filtering/native top-k, but requires a new persisted schema or a new direct coupled DataFusion dependency/custom execution code. Neither is part of the approved schema-preserving adapter; surface a concrete Operator choice before that route.
- Stream a projected plain scan of metadata and native row IDs, accumulate a bounded batch of matching row IDs, then ask native vector search for at most k results restricted to that batch, merge only bounded global top-k. Recommendation for a bounded private adapter, subject to actual SDK/runtime proof: no data rewrite, no new dependency/public API, unchanged native distance kernel. Plain Query defaults to no row limit; Select::columns and with_row_id select only required columns; execute_with_options has bounded batch/backpressure documentation. Native Lance14 scanner.rs1341–1357/1429–1443 explicitly supports `_rowid IN (...)`, including an AND remainder, and tests20367–20415 cover native row-ID predicates. Use numeric owned row IDs rather than external string IDs to avoid duplicate-ID false positives, literal escaping and unbounded ID sets. Do not assume query output order; merge top-k by actual returned distance/score. At most a fixed batch of row IDs, one record batch and k retained results; no all-N Vec/HashMap/heap/querylimit. An empty/zero-limit query must terminate correctly.

The recommended adapter still reads O(N) metadata and may perform ceil(M/batch) vector queries for M matches; latency is a real disclosed tradeoff versus a hypothetical fused JSONB predicate, not a claimed benchmark improvement. Existing flat search already evaluates distances across unindexed data, but that does not justify pretending the new two-phase latency is identical.
