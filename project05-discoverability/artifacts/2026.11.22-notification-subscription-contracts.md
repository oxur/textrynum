## Version and ownership map

At source 719, `FabrykMcpServer::get_info` advertises resource subscriptions only when a resource registry exists (`server.rs:351–377`). `on_initialized` adds `context.peer` to the notifier’s global peer list (`server.rs:379–391`). The server is `Clone` and contains a `Notifier` (`server.rs:75–82`); the HTTP service factory clones the server (`server.rs:248–260`). `Notifier` clones share the global peer and URI subscription maps through `Arc<RwLock<...>>` (`notifier.rs:27–41`), and `lib.rs:47–75` exposes `notifier` and re-exports `Notifier` and `FabrykMcpServer`.

The public SDK constants are `LATEST = 2026-07-28` and `LATEST_WITH_INITIALIZE = 2025-11-25` (`rmcp/src/model.rs:168–201`). `uses_legacy_lifecycle` returns true only when the request is not using discover lifecycle and the negotiated protocol is absent or still has initialize (`rmcp/src/service.rs:241–247`). Dispatch routes legacy subscribe/unsubscribe only on that path (`rmcp/src/handler/server.rs:216–233`). Thus the source composition below applies to reachable initialized compatibility sessions; this evidence does not establish that every current client uses that path. `LATEST` being 2026 does not itself prove which version any live session negotiates. The default `accepted_subscription_filter` returns `None`, while default `listen` waits for cancellation (`rmcp/src/handler/server.rs:534–560`); absence of a server-specific 2026 listen implementation is not treated as a defect here.

The 2025-11-25 resource specification says clients subscribe to request subsequent resource updates and unsubscribe to cancel the client’s subscription. ResourceUpdated guidance targets subscribers; ResourceListChanged has separate guidance that permits unsolicited notification. These are distinct notification types. The specification uses SHOULD-level language; this report does not invent an exactly-once delivery contract. Sources: [2025-11-25 server resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources) and [2025-11-25 schema](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-11-25/schema.ts).

## Manual case A — mixed update/prune attempts

Assumptions: explicit URI map contains A and B; A’s `notify_resource_updated` method succeeds on both passes; B’s method fails on both passes; the subscription map does not change concurrently. This is source-state reasoning only.

| Step | Map/branch | A method attempts | B method attempts | Returned-success accounting |
| --- | --- | ---: | ---: | --- |
| First pass | Snapshot `[A,B]`; one call per snapshot peer (`notifier.rs:107–118`) | 1 success | 1 failure | `success = 1` |
| Failure handling | Any first-pass failure enters a second loop over the current URI map (`:119–124`) | — | — | Returned value remains first-pass count |
| Second pass | Construct a new `ResourceUpdatedNotificationParam` per current peer and call again (`:125–135`) | +1 success | +1 failure, then remove B with `swap_remove` | Still 1; it is not a count of all method attempts |
| End state | Remove URI entry only if the post-prune list is empty (`:136–141`) | A remains | B removed | No client delivery/read was observed |

The all-success branch makes one method attempt per snapshot peer and skips pruning. When no explicit subscription entry exists, the documented backwards-compatible branch broadcasts once to the global peer list and prunes first-pass failures by reverse snapshot indices (`notifier.rs:142–158`). `resource_list_changed` separately sends once to the global peers and prunes in reverse index order (`:161–179`); logging follows a similar one-pass pattern (`:49–74`). The `rmcp` peer methods wrap `send_notification` and return its method result (`service/server.rs:790–800, 945–960`). A successful method result is not evidence of actual client receipt or processing.

## Manual case B — two initialized peers and unsubscribe composition

Assumptions: global initialized-peer list is `[A,B]`; both clients’ legacy subscriptions for URI `u` remain live except for the caller’s own unsubscribe request; all calls share one notifier; no concurrent changes. This is a manual state trace, not an RPC operation.

| Operation | Global peers | Explicit `u` map | Update recipients selected by source |
| --- | --- | --- | --- |
| Initial state | `[A,B]` | absent | Fallback would broadcast to `[A,B]` |
| A subscribes `u` | `[A,B]` | `[A]` | Target A |
| B subscribes `u` | `[A,B]` | `[A,B]` | Target A and B |
| A calls legacy unsubscribe | `[A,B]` | entry removed URI-wide | No-entry fallback may still broadcast to A and B; do not claim immediate loss for B |
| A subscribes again | `[A,B]` | `[A]` | Target A only |
| Update after resubscribe | `[A,B]` | `[A]` | B is omitted from explicit targeted delivery although the scenario did not cancel B’s subscription |

The callback passes `context.peer` to `subscribe_resource` (`server.rs:437–448`) but names the unsubscribe context `_context` and invokes URI-wide `unsubscribe_resource` (`:452–461`). The helper explicitly documents removal of every peer for that URI because `Peer` lacks `PartialEq` (`notifier.rs:86–93`). That bulk helper policy is deliberate contrary evidence, not an undocumented defect in the helper considered alone. The server callback’s use of it for a caller-specific operation is the distinct composition concern.

## Contrary controls and limits

1. All-subscriber success takes one send pass; the second sweep is failure-triggered (`notifier.rs:112–120`).
2. The no-entry global broadcast is explicitly documented as backwards compatibility (`:95–100,142–158`), not accidental targeting.
3. URI-wide unsubscribe is explicitly documented because `Peer` lacks `PartialEq` (`:86–93`); preserve that public helper’s bulk behavior unless a separately authorized compatibility decision changes it.
4. ResourceListChanged is a separate global one-pass operation, not evidence for ResourceUpdated subscriber semantics (`:161–179`; versioned protocol sources above).
5. Legacy callback dispatch is lifecycle-gated; findings are scoped to initialized compatibility sessions, not all clients (`rmcp/src/service.rs:241–247`; `handler/server.rs:216–233`).
6. Default 2026 `listen` behavior and missing optional hooks are not used as defects (`handler/server.rs:534–560`).
7. `success` counts successful first-pass method calls in the explicit branch, not total calls or client receipts (`notifier.rs:113–141`).
8. No source-backed idempotence promise for repeated subscribe was established; duplicate-subscribe behavior remains a question, not a finding.
9. Prune-time list changes are read from the current map under a write lock, so the second pass can differ from the earlier snapshot. Any future repair must reconcile identities/concurrent changes; it must not apply stale snapshot indices to a later vector or assume `Peer: PartialEq`.

## Proposed diagnoses

Two separate source mechanisms are proposed below. Both are pinned to source revision 719, and both remain subject to independent CDC review. Full diagnosis text appears once in the cumulative Rust report.

- **FA-RS-040, Low, CC-proposed:** a failure on any explicit subscriber causes a second `notifications/resources/updated` method attempt to every current URI subscriber, including peers whose first call succeeded. Concern: redundant notification attempts and possible repeated client work. No duplicate client receipt, exactly-once violation, or measured impact is claimed.
- **FA-RS-041, Medium, CC-proposed:** in the reachable legacy initialized callback path, one caller’s unsubscribe removes every peer’s URI entry. The no-entry broadcast can temporarily mask the removed peer; after the caller resubscribes alone, subsequent explicit targeted updates omit the other still-subscribed peer in the stated sequence. The helper’s bulk API is an intentional control; the finding is the server-level callback composition against the per-client unsubscribe contract.

Logical owner for both proposed follow-ups: `fabryk-mcp-core` notifier/server maintainers. These are future repair directions, not current repair authority. For 040, separate failed-registration pruning from resending to already-successful peers; reconcile the failed peer identity with concurrent map changes without stale indices or a `PartialEq` assumption. If repeated sends are intentional, document their policy and caller-visible meaning. For 041, keep the public bulk helper compatible while the server callback removes only the calling peer’s registration using a stable identity/token strategy; do not prescribe a protocol migration. Future discriminating checks should count method invocations separately from client receipts for 040, and apply the stated A/B subscribe/unsubscribe/resubscribe sequence for 041, with additional concurrent subscribe/unsubscribe cases. None were run.
