## Cross-file contracts and architecture

### Construction, public facade, and tool dispatch

`ServerBuilder` is an ergonomic composition path, not a validator: it appends registries in order and builds the server (`builder.rs:94–180`). The facade exposes the core pieces from `lib.rs:47–110`; HTTP exports require the `http` feature (`lib.rs:148–162`, `Cargo.toml:33–38`). `CompositeRegistry::tools` concatenates each registry’s returned vector and `call` tries each in insertion order (`registry.rs:104–117`). Duplicate names can therefore appear in listings and the first registry returning `Some` wins. `validate_tools` does diagnose duplicate names (`validate.rs:175–197`), but the server/builder path does not call it automatically. The builder documents insertion order; neither a dispatch ambiguity nor the existence of validation alone proves a required startup failure policy. No finding is proposed for this behavior; the owner decision whether duplicates should be warnings, errors, or intentional overrides remains open.

The server stores the registry in `Arc<dyn ToolRegistry>` and clones it for HTTP service instances; notifier and optional resources are clone-shared too (`server.rs:75–93,243–260`). Tool call arguments are converted from an optional object to `Value::Null` when absent (`server.rs:403–415`). Unknown tool names become an MCP tool-error result rather than an `Err(ErrorData)` (`server.rs:301–313`). This distinction is source-visible but no broader client UI behavior is claimed.

### Discovery metadata and currentness

`DiscoverableRegistry` constructs tool descriptions from `ToolMeta`, generates the directory tool, and serializes tool/category and optional metadata sections (`discoverable.rs:311–553`). Empty optional sections are omitted; a deliberately slim projection is sound when its recovery path is useful. The directory does not serialize every internal registry field. Existing tests cover keys, omission, task recipes, IDs, status and serde shape, but not whether an agent chooses the intended next call (`discoverable.rs:686–1473`).

Three current contract tensions are proposed below, with separate scopes:

1. `with_task_strategies` documentation says the task recipes replace the flat query strategy, but directory construction emits the flat `optimal_query_strategy` from `query_strategy` and separately emits `query_strategies` when task strategies exist (`discoverable.rs:389–429,502–508`). The test explicitly says both may appear because they use different keys (`:1174–1203`). `ServerGuidance.workflow` feeds that flat strategy (`:204–225`). This is a consistency issue in a single directory response, not evidence of client selection.
2. `BackendStatus` is an owned value installed by a consuming builder method and held as `Option<BackendStatus>` (`discoverable.rs:166–181,272–276`). Each directory call serializes the stored value (`:495–500`); there is no call-time callback or mutation API. The metadata how-to calls this “what works right now” and directs callers to query service state at directory-call time (`docs/howtos/mcp-metadata.md:840–842,875–878`), while its code sample evaluates readiness when building the registry (`:626–640`). A long-lived server can therefore serve stale readiness after lifecycle changes. This is bounded to the documented dynamic status claim and status users; it does not imply all metadata must be live.
3. `StaticResources::read` falls back for every `read_to_string` error, although the public docs describe fallback when a file does not exist (`static_resources.rs:30–35,91–106`). Permission, invalid UTF-8, and other I/O errors are not distinguished from absence. Only missing-file fallback is covered by source tests (`:176–211`). The consequence is that a configured fallback can hide a resource read failure and return stale/default text; no actual filesystem failure was induced.

### Health, service gates, and backend resolution

These policies are distinct in source and docs; they are not collapsed into one global state model:

- `FabrykMcpServer::is_ready` requires every registered service to be Ready and is vacuously true for no services (`server.rs:126–129`; tests `:625–654`).
- `ServiceAwareRegistry` permits Ready or Degraded for calls but leaves tools listed in all states (`service_registry.rs:22–79`; tests `:122–194`).
- `health_router` returns 200 for Ready/Stopped and 503 otherwise, including Degraded (`health_router.rs:61–112`; docs `docs/howtos/mcp-health.md:12–20,99–119`).
- `DiagnosticTools::service_status` calls the overall state ready only if every state is Ready (`tools/diagnostics.rs:102–121`).
- `HealthTools` returns status `healthy` while separately reporting boolean probe readiness (`tools/health.rs:147–199`).

The health how-to explicitly treats Stopped as unconfigured and healthy. These differences can serve different operational, invocation-gating, and diagnostic purposes. No finding demands parity; later owners may clarify a caller’s particular expectation if evidence identifies one.

`resolve_search_backend` requires slot readiness, lock acquisition, and a populated backend, then otherwise falls back to the supplied simple backend; `resolve_backend_name` uses only readiness (`search_fallback.rs:59–86`). This small identity/readiness asymmetry can occur if a slot reports Ready while empty or unreadable. The static API does not establish that such slot states are supported or that a name must always identify the returned object, so it remains an ungraded owner question rather than a forced defect.

### Resource, error, lifecycle, and protocol adapter

Resource capability advertisement depends on whether a registry is installed, not whether its list is nonempty (`server.rs:346–377`; test `:703–723`). Reads without a registry and unknown URIs map to invalid-params in the Fabryk handler (`:323–343`). Static file errors use resource-not-found only when no fallback is configured (`static_resources.rs:91–106`). The selected locked RMCP 3.11.0 `handler/server.rs:328–335` remaps resource-not-found to invalid-params for protocol 2026-07-28+ while retaining the older code for older peers. This adapter evidence blocks an obsolete-error-code diagnosis based solely on Fabryk’s `ErrorData::resource_not_found` construction. It is compatibility evidence from the locked dependency source, not an audit of RMCP itself.

Resource list advertises each configured MIME value but static reads construct `ResourceContents::text`, whose observed source-level HTTP test expects `text/plain` even when the listed resource says `text/markdown` (`static_resources.rs:72–109`; `server.rs:960–1112`). Existing text/plain compatibility evidence is preserved; no forced parity finding is proposed.

`get_info` enables tools/logging always and resources/subscribe/list-changed when a resource registry exists (`server.rs:346–377`). The handler wires legacy `subscribe`/`unsubscribe` into the notifier (`:436–462`). RMCP 3.11.0 selects those callbacks only for legacy requests and has a separate opt-in `accepted_subscription_filter`/`listen` path for modern subscriptions (`handler/server.rs:178–233,534–580`). The absence of the optional modern listener is not treated as a defect. Existing FA-RS-040 and FA-RS-041 remain separate accepted roots for notification resend/pruning and the legacy per-caller unsubscribe composition; neither is duplicated here.

`McpErrorExt` maps NotFound/FileNotFound, parse/YAML, config and JSON errors; `McpErrorContextExt` has its own smaller policy (`error.rs:15–56`). Handlers may return either MCP error data or `CallToolResult::error`; source alone does not establish a common UI treatment. Diagnostics redaction is intentionally narrow and docs direct callers to preprocess custom secrets (`tools/diagnostics.rs:26–30,85–100`). No generic redaction finding is proposed.

### Docs, configuration, async, and ownership boundaries

The crate README marks current 0.5 source compatibility and historical published `0.2` usage separately (`crates/fabryk-mcp/README.md:1–82`). The metadata how-to claims 1-call discoverability and current backend status; these are documentation intent, not client evidence. The health and async-startup how-tos document separate service/readiness use. `StaticResources` accepts caller-defined filenames and joins them to a base path (`static_resources.rs:15–27,84–109`); no request directly supplies that filename in this slice. Path containment is therefore retained as a configuration-owner question, not asserted as an externally reachable traversal defect.

Static resource reads call `std::fs::read_to_string` within the returned async future (`static_resources.rs:91–109`), so filesystem work itself is synchronous. The API is explicitly a static-resource helper, and no size/load/concurrency promise in the assigned inputs establishes a harmful workload. This is recorded as an async/performance boundary, not a severity-graded finding. Notifier operations await peer sends while holding the peers write lock for broadcast paths (`notifier.rs:57–74,142–179`); fan-out is serialized and can block mutations during sends, but there is no source-level throughput contract or observed slow peer. It remains a concurrency/load proof gap, not a new finding or duplicate of 040.
