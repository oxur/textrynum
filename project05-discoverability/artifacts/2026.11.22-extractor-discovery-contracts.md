## Processing timing and error/cache boundaries

- **Graph cold build:** `GraphBuilder::build` first requires `content_path` (`graph/builder.rs:155–160`). If cache is enabled and fresh, it returns before discovery (`:162–185`). Otherwise it discovers at `:188–190`, then processes each returned path and calls graph extraction (`:211–239, 307–330`). Parse/extraction errors follow FailFast or Collect/Skip (`:222–235`); discovery errors propagate through `?`. Manual edges are a later phase (`:278–283`).
- **Vector cold build:** requires both `content_path` and provider before cache (`vector/builder.rs:130–145`). A fresh cache can return before discovery (`:147–174`). Otherwise discovery is at `:176–178`, extraction/error policy at `:187–213, 260–275`, and embedding follows extraction. FailFast returns; Collect records a skipped-file error; Skip records/logs it (`:192–210`).
- **Vector append:** requires content path and provider (`:301–317`), then discovers at `:318–319`; there is no cache-hit branch in this method. Extraction/error policy follows at `:325–352`.
- **Core walk:** `find_all_files` propagates walker-entry errors (`core/util/files.rs:162–164`), skips directories (`:166–169`), applies optional max depth (`:171–180`) and exact extension filtering (`:182–187`), then records each relative path (`:189–201`). For the fixed Markdown options this is recursive with no explicit depth cap and accepts only paths whose extension string is exactly `md`.

The graph cache freshness helper and vector content hash currently derive from Markdown files, not a consumed extractor glob (`graph/builder.rs:413–456`; `vector/builder.rs:408–428`). This assessment does not diagnose cache behavior. ## Contrary controls and questions

1. Both stock concept-card extractors use the default `**/*.md`, and tests assert that default. The fixed Markdown selector is not a defect for that default population.
2. Callers can narrow the entire input root with `with_content_path`; this remains useful when the desired content is already isolated by directory. It does not express a filename filter within the stated shared root.
3. `FindOptions` supports extension and depth for direct core utility callers; it does not expose glob selection, and the two builder APIs do not accept it.
4. Extractor methods can be called directly after a caller’s own selection; this is a separate manual composition path, not evidence that `GraphBuilder` or `VectorIndexBuilder` honors the method.
5. `GraphBuilder::with_manual_edges` supplies edge JSON after node discovery and cannot narrow discovered documents.
6. Missing required root/provider and cache hits precede the applicable discovery path; no extractor call is expected on those exits. Vector append has no cache early return but still checks path/provider first.
7. The assigned scenario is deliberately Markdown-only. It does not establish a promise for arbitrary non-Markdown extensions.
8. `**/` root-level matching and broader glob semantics are assumptions to make the requested manual case discriminating; no matcher/dependency semantics are claimed.
9. Search was bounded to the two named crates and selected core utility. No claim is made about all workspace consumers or unrelated discovery abstractions.

Open decisions if the owning APIs are revised: honor `content_glob` in both named builders with an explicit pattern dialect, root-relative path rules, extension interaction, exclusion/depth behavior and invalid-pattern error handling; or revise/remove the promise so callers are not told it controls builder discovery. Keep `**/*.md` default behavior compatible. Any implementation must update both graph/vector builder paths consistently without assuming helper similarity requires centralization. Align any later cache population/freshness rule with the selected file population. No decision or repair is made here.
