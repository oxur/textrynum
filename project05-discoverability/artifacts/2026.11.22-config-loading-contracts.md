## Manual contract interpretation

The port option stores a name, but build(self, ...) neither reads it nor
returns it; check_port_override(&self) is separately callable but described as
post-build, impossible on that consumed value. Caller-owned application remains
possible by checking before build and applying afterward. The how-to separately
reads/applies PORT after build (:110–123), but deployment prose attributes the
override to registering the option (:313–314). FA-RS-036 is limited to that
option/call-order/documentation mismatch, not a claim all callers cannot apply
PORT.

The guide calls Self::resolve_config_path() at mcp-configuration.md:115,140
although its shown ConfigManager signature takes explicit: Option<&str> at
:136–140; it calls Config::load() at :214 though the same sample defines
load(config_path: Option<&str>) at :101–103. Current FabrykConfig definitions
also take the optional path (config.rs:107,135,174–180). Omitted inherent
wrappers are possible, so no compile error is asserted. The shown generic
entrypoints do not demonstrate calls matching their shown signatures.
CDC retains FA-RS-037 as an unresolved documentation question because surrounding
inherent wrappers may be omitted; the textual gap alone does not prove a
consumer-contract failure. The author proposed it as Low at e435422c. The separate
server guide shows load(config_path) at lines 193–197 as a contrary control.

The generic loader accepts a resolver closure; FabrykConfig has concrete prefix,
section and path-precedence policy. These overlap in responsibility but are
different policy layers; no consolidation demand follows.

## Negative checks and contrary evidence

1. Port helper only reads/parses and returns Option<u16>; no environment mutation (config_loader.rs:123–132).
2. build loads an existing resolved file, adds configured prefix/sections, returns config/path and reports errors (config_loader.rs:88–120); no general loader defect alleged.
3. Caller owns applying the override (:63–74); check-before-build remains possible, so “all callers cannot apply PORT” is rejected.
4. FabrykConfig precedence is explicit path, FABRYK_CONFIG, XDG (config.rs:134–153), a concrete implementation.
5. ConfigManager delegates to inherent loading/path/serialization/export (config.rs:174–198); declarations alone are not defects.
6. ConfigProvider domain paths/default cache and ConfigManager loading/CLI with different bounds are intentional boundaries (traits.rs:49–50,70–81,155–191).
7. Generic FabrykCli construction/concrete FabrykConfig dispatch is documented, with generic handlers explicitly offered (app.rs:21–32,75–104; config_handlers.rs:18–50); no dispatch defect claimed.
8. Separate server guide shows load(config_path); no compiler result claimed.
9. CLI actions and generic handlers cover path/get/set/init/export (cli.rs:80–130; config_handlers.rs:21–41,48–50,68–89,102–109,132–172); no broad CLI omission alleged.
