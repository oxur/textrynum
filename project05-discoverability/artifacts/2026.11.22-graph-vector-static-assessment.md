## Cross-file architecture and current contracts

### Graph construction, storage, and query

`GraphExtractor` separates domain extraction from graph storage; `GraphBuilder` discovers Markdown, synchronously parses each file, adds all nodes, then resolves edges in a second phase. It records skipped-file errors, dangling references, deduplication and cache status (`fabryk-graph/src/builder.rs:148–330`). `GraphData` mirrors a petgraph `DiGraph` with public node-index, node, and flat-edge collections. Its API makes duplicate node insertion first-wins and rejects missing edge endpoints, but permits parallel edges (`types.rs:385–490`). Direct public field access can bypass those wrapper invariants; this review does not assume arbitrary caller mutation is a supported invariant-preserving path.

The stock concept-card extractor maps frontmatter relationship fields into typed edges. The accepted FA-RS-038 direction finding and FA-RS-045 filter/parser finding remain in force; the per-file matrix records their affected loci without re-proposing them. Algorithms preserve distinct contracts: prerequisite direct/recursive routes have the accepted orientation inconsistency; shortest-path uses an internal transformed edge cost, while path policy/provenance/ties remain slice19 questions; neighborhood filtering uses typed relationships. Query types project the graph into response records and emit canonical relationship names (`query.rs:45–66,73–90`). No new canonical direction, metric, tie, or edge-provenance promise is chosen.

GraphBuilder cache freshness differs from the separate feature-gated rkyv helper: the ordinary builder hashes sorted relative Markdown paths plus whole-second modification times (`builder.rs:413–456`); the rkyv helper hashes file bytes (`persistence.rs:172–220`). The ordinary cache-hit check happens before discovery and manual-edge loading (`builder.rs:162–185`). The builder’s public cache description says content hashes (`builder.rs:131–136`), while its helper explicitly says it hashes paths and mtimes, not contents (`:413–416`). A same-path Markdown content change within the same second can therefore leave the ordinary key unchanged. A separate caller-policy question remains for manual-edge files, extractor behavior, or builder version: this source does not specify whether callers must partition cache paths or how those inputs should enter freshness.

JSON persistence stores nodes, edges and optional metadata; it rebuilds the directed graph and silently skips edges whose endpoints are absent (`persistence.rs:76–165`). Orphan nodes and duplicate endpoint/name edges are warnings; `add_warning` leaves `valid` unchanged. Self-loops, prerequisite cycles, and broken canonical references are errors (`validation.rs:29–54,138–181,184–213,248–279`). The duplicate key is endpoints plus `Relationship::name()`, not weight or origin. Cycle validation builds a prerequisite-only subgraph; non-prerequisite cycles are intentionally allowed (`validation.rs:216–246,469–485`). Statistics report graph counts, degree distributions, category/type/relationship counts and orphan counts; equal-degree winner order is not promised (`stats.rs:63–190`).

The graph feature contract is incomplete: Cargo declares `graph-rkyv-cache` at `Cargo.toml:12–14`; README and crate docs describe optional rkyv persistence (`README.md:10–17`; `lib.rs:8–10`), and the feature-gated re-export is at `lib.rs:74–75`. The `rkyv_cache` module only computes byte hashes and exposes no rkyv save/load path (`persistence.rs:172–221`); the public save/load API is JSON (`persistence.rs:76–165`). This supports proposed FA-RS-046; its corrected full entry is in the cumulative report.

### Vector construction, backend, and retrieval

`VectorExtractor` promises a per-domain content glob. `VectorIndexBuilder` currently uses `FindOptions::markdown()` directly and never calls `content_glob`; this is the accepted FA-RS-042 contract root. The stock concept-card vector extractor composes title/category/subcategory/description/aliases/questions/body text, derives IDs from paths, and emits category/source/chapter metadata (`concept_card_extractor.rs:38–105`).

The builder has required content path/provider inputs, error policies, batching, a content-byte hash cache, and an append path. It hashes sorted path+content bytes, unlike GraphBuilder’s mtime helper (`builder.rs:119–257,277–390,398–428`). The public batch-size setter stores zero without validation; if a build/append reaches `documents.chunks(self.batch_size)`, `chunks(0)` panics. Earlier missing-input, cache-hit, and other exits can prevent that call; accepted FA-RS-039 remains the one bounded precondition finding (`builder.rs:96–100,130–173,220,357`). Returned provider embeddings are paired with documents using `zip`, so the existing custom-provider cardinality question remains open; default and mock providers emit one-per-input (`embedding.rs:25–46,91–111`; `builder.rs:220–227,357–364`). Append accepts an independently supplied provider; its public example deliberately reuses the same provider instance, and the accepted slice15 questions about provider identity and cache partition remain unchanged.

The backend factory accepts `VectorConfig` and an already-created provider. Its public selection docs say an enabled `vector-lancedb` plus `lancedb` config selects `LancedbBackend`, but that feature-gated branch intentionally returns `SimpleVectorBackend` and points to the separate async `LancedbBackend::build` (`backend.rs:54–79`; `lancedb.rs:54–70`). FA-RS-053 records this narrow public-doc mismatch; it does not require changing the fallback or adding an async factory. Separately, the factory reads only `enabled`/`backend` and does not construct a provider or consume the other `VectorConfig` fields (`types.rs:14–105`). The CLI constructs `FastEmbedProvider` from caller values rather than wiring `VectorConfig` (`fabryk-cli/src/vectordb_handlers.rs:15–48`); the broader config-assembly question Q04-GV-02 remains open.

`VectorSearchResults.total` is documented as total matching documents (`types.rs:259–270`), but both backends count after the limit has constrained retrieval (`backend.rs:264–288`; `lancedb.rs:113–160`). This is the source basis for proposed low-severity FA-RS-048. It is not a claim that all matches were lost from storage; the unresolved owner choice is whether `total` means all matches or returned items.

FastEmbed maps four names/aliases, probes dimension during construction, then captures `Arc<Mutex<_>>` in `spawn_blocking`; the module comment asserts the dependency type is not `Send + Sync` (`:6–9`), but this review does not promote that auto-trait claim because no Cargo/build or dependency trait check ran; initialization, poison, provider, and task-join errors are converted to `Result` errors (`fastembed.rs:20–31,52–88,91–145`). Its download-dependent tests are ignored. Hybrid search performs reciprocal-rank fusion over positions rather than source scores; duplicate IDs accumulate scores and source flags, while metadata is taken from the first occurrence (vector list processed first) (`hybrid.rs:66–124`). The probe delegates name/readiness/document-count; readiness inherits `VectorBackend::is_ready() == true`, and count errors become `None` (`probe.rs:30–64`; `backend.rs:34–52`). These are current APIs only, not readiness, model download, database, retrieval, or service execution evidence.

### A — unrelated graph cycle and prerequisite result (FA-RS-049)

`prerequisites_sorted` gathers only incoming typed prerequisites, then calls `toposort` on the full graph; any `Err` falls back to `HashSet` iteration and sets `has_cycles=true` (`fabryk-graph/src/algorithms.rs:286–337`). The pinned petgraph 0.8.3 `toposort` source documents an error for a cyclic input (`/Users/oubiwann/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/petgraph-0.8.3/src/algo/mod.rs:187–205`). The prerequisite-only validator permits the separate `RelatesTo` cycle (`validation.rs:216–246,469–485`). `LearningPathResult.has_cycles` describes cycles in the prerequisite graph; `learning_path` forwards the result, and MCP exposes the fields (`algorithms.rs:569–601`; `types.rs:103–113`; `fabryk-mcp-graph/src/tools.rs:1001–1021`). I classify the supported chain-plus-unrelated-cycle case as a low-severity API contract mismatch. The fallback order is unspecified; no particular sequence or client output is claimed. No-cycle, genuine prerequisite-cycle, no-prerequisite and missing-target cases remain controls.

### B — multirelationship graph and degree normalization (FA-RS-050)

`GraphData::add_edge` accepts parallel edges (`fabryk-graph/src/types.rs:471–489`); duplicate validation keys by relationship name. With two nodes and three distinct relationship kinds from `AcmeA` to `AcmeB`, the source formula counts three edges and divides by `2(n−1)`, so degree is 1.5 (`algorithms.rs:344–364`), beyond the `CentralityScore.degree` 0–1 promise (`types.rs:77–88`). This is a low-severity source-derived range mismatch, not a measured return. The finding does not impose a range on `in_degree` or `out_degree`. Existing centrality tests use the ordinary fixture and do not cover multirelationship edges (`algorithms.rs:882–908`); one-edge and fewer-than-two-node cases are controls.

### C — zero maximum for bridge results (FA-RS-051)

MCP accepts an optional `usize` limit and its schema has no positive minimum (`fabryk-mcp-graph/src/tools.rs:168–177,638–655`). The handler passes the value unchanged (`:1024–1035`). The bridge routine appends a qualifying node before checking `results.len() >= limit` (`fabryk-graph/src/algorithms.rs:609–650`), so with `AcmeX` connected to nodes in both requested categories and `limit=0`, a supported zero maximum can admit one result. The current “Maximum results” promise supports a low-severity bound mismatch. The iteration-selected node is not predicted. Existing positive-limit and no-match tests are controls (`algorithms.rs:1337–1352`); zero was not tested or run.

### D — parallel neighborhood edges (FA-RS-052)

The public function says it collects all edges within radius and the result field describes edges connecting neighborhood nodes (`fabryk-graph/src/algorithms.rs:120–137`; result fields at `:28–38`). But the traversal appends an edge only when `visited.insert(neighbor_idx)` succeeds (`:164–201`). With two supported, distinct relationship edges from `AcmeA` to `AcmeB`, with `AcmeA` the radius-zero center and `AcmeB` the radius-one neighbor and no filter, only the discovery edge is recorded. MCP returns the edge array and its count (`fabryk-mcp-graph/src/tools.rs:765–803`). I classify this narrowly as a low-severity current documentation/implementation mismatch; I do not infer full induced-subgraph semantics or which edge is chosen. Single-edge, each individual relationship filter and radius-zero cases are controls; the current basic/radius/filter tests do not cover parallel-edge multiplicity (`algorithms.rs:734–786`).

### Vector factory selection claim (FA-RS-053)

The public `create_vector_backend` docs say enabled LanceDB selection returns `LancedbBackend`, while the gated branch returns `SimpleVectorBackend` and explicitly points to async `LancedbBackend::build` (`fabryk-vector/src/backend.rs:54–79`; `lancedb.rs:54–70`). The source-supported disposition is a narrow public-doc inconsistency. Keep the current fallback as a valid policy and correct its selection prose; do not require feature parity or an async factory redesign. This is distinct from Q04-GV-02’s caller-owned `VectorConfig` assembly scope.
