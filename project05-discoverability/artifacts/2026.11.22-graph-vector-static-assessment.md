## Cross-file architecture and current contracts

### Graph construction, storage, and query

`GraphExtractor` separates domain extraction from graph storage; `GraphBuilder` discovers Markdown, synchronously parses each file, adds all nodes, then resolves edges in a second phase. It records skipped-file errors, dangling references, deduplication and cache status (`fabryk-graph/src/builder.rs:148–330`). `GraphData` mirrors a petgraph `DiGraph` with public node-index, node, and flat-edge collections. Its API makes duplicate node insertion first-wins and rejects missing edge endpoints, but permits parallel edges (`types.rs:385–490`). Direct public field access can bypass those wrapper invariants; this review does not assume arbitrary caller mutation is a supported invariant-preserving path.

The stock concept-card extractor maps frontmatter relationship fields into typed edges. The accepted FA-RS-038 direction finding and FA-RS-045 filter/parser finding remain in force; the per-file matrix records their affected loci without re-proposing them. Algorithms preserve distinct contracts: prerequisite direct/recursive routes have the accepted orientation inconsistency; shortest-path uses an internal transformed edge cost, while path policy/provenance/ties remain slice19 questions; neighborhood filtering uses typed relationships. Query types project the graph into response records and emit canonical relationship names (`query.rs:45–66,73–90`). No new canonical direction, metric, tie, or edge-provenance promise is chosen.

GraphBuilder cache freshness differs from the separate feature-gated rkyv helper: the ordinary builder hashes sorted relative Markdown paths plus whole-second modification times (`builder.rs:413–456`); the rkyv helper hashes file bytes (`persistence.rs:172–220`). The ordinary cache-hit check happens before discovery and manual-edge loading (`builder.rs:162–185`). The builder’s public cache description says content hashes (`builder.rs:131–136`), while its helper explicitly says it hashes paths and mtimes, not contents (`:413–416`). A same-path Markdown content change within the same second can therefore leave the ordinary key unchanged. A separate caller-policy question remains for manual-edge files, extractor behavior, or builder version: this source does not specify whether callers must partition cache paths or how those inputs should enter freshness.

JSON persistence stores nodes, edges and optional metadata; it rebuilds the directed graph and silently skips edges whose endpoints are absent (`persistence.rs:76–165`). Orphan nodes are warnings; self-loops, prerequisite cycles, and broken canonical references are errors. Non-prerequisite cycles are deliberately outside the cycle check (`validation.rs:117–279,469–485`). Duplicate-edge validation keys by endpoints plus `Relationship::name()`, not edge weight or origin (`validation.rs:184–213`). Statistics report graph counts, degree distributions, category/type/relationship counts and orphan counts; equal-degree winner order is not promised (`stats.rs:63–190`).

The graph feature contract is incomplete: Cargo gates `rkyv`, `memmap2`, and `blake3` under `graph-rkyv-cache`; README and crate docs describe optional rkyv persistence; the feature-gated public module only computes byte hashes and exposes no rkyv save/load path (`Cargo.toml:15–20`; `README.md:10–17`; `lib.rs:1–10,64–77,109–111`; `persistence.rs:172–221`). JSON save/load remains the implemented persistence API (`persistence.rs:76–165`). This supports proposed FA-RS-046; it does not establish whether the intended owner outcome is implementing binary persistence or correcting the feature/docs/dependency claim.

### Vector construction, backend, and retrieval

`VectorExtractor` promises a per-domain content glob. `VectorIndexBuilder` currently uses `FindOptions::markdown()` directly and never calls `content_glob`; this is the accepted FA-RS-042 contract root. The stock concept-card vector extractor composes title/category/subcategory/description/aliases/questions/body text, derives IDs from paths, and emits category/source/chapter metadata (`concept_card_extractor.rs:38–105`).

The builder has required content path/provider inputs, error policies, batching, a content-byte hash cache, and an append path. It hashes sorted path+content bytes, unlike GraphBuilder’s mtime helper (`builder.rs:119–257,277–390,398–428`). The public batch-size setter accepts zero and both build/append paths reach `slice::chunks`; accepted FA-RS-039 remains the calibrated low-severity precondition. Returned provider embeddings are paired with documents using `zip`, so a custom provider’s short or long batch silently drops one side; default and mock providers return one-per-input by construction, so the prior question remains ungraded rather than a built-in defect (`embedding.rs:25–46,91–111`; `builder.rs:220–227,357–364`). Append accepts an independently supplied provider; its public example deliberately reuses the same provider instance, and the accepted slice15 questions about provider identity, cache partition and cardinality remain unchanged.

The backend factory accepts `VectorConfig` and an already-created provider. It reads `enabled` and `backend`; it returns `SimpleVectorBackend` for disabled, unknown, and `lancedb` choices, with a comment directing callers to `LancedbBackend::build` for async initialization (`backend.rs:54–79`). This is current documented fallback behavior, not an all-feature parity finding. `VectorConfig` also carries provider/model/dimension/storage/content/cache/default-search fields (`types.rs:14–105`), but this factory does not construct a provider or use those fields. The CLI’s current `get-model` handler receives model/cache values from its caller and directly constructs `FastEmbedProvider`; it does not wire `VectorConfig` (`fabryk-cli/src/vectordb_handlers.rs:15–48`). Whether `VectorConfig` is a descriptor for external application assembly or a runnable crate-level construction contract remains an ungraded question.

`SimpleVectorBackend` is in-memory O(n) cosine search. It returns empty before embedding on an empty store, maps unequal/empty/zero-norm vectors to score 0, applies threshold and exact category/metadata filters, sorts, truncates, then sets `total` to the truncated item count (`backend.rs:98–129,205–219,223–288`). LanceDB derives fixed-list width from provider dimension, creates/overwrites a table only for nonempty input, returns empty before query embedding when its document count is zero, and exposes category/threshold/limit/metadata-filter branches (`lancedb.rs:54–103,106–170`). Metadata filtering scans metadata rows, matches all key/value pairs, gathers row IDs in batches of 128, performs restricted vector queries and merges/sorts/truncates the collected results (`:172–292`). It converts Lance distance to score as `1/(1+distance)` (`:379–423`), which is not claimed to be the same scale as Simple’s cosine similarity.

`VectorSearchResults.total` is documented as total matching documents (`types.rs:259–270`), but both backends count after the limit has constrained retrieval (`backend.rs:264–288`; `lancedb.rs:113–160`). This is the source basis for proposed low-severity FA-RS-048. It is not a claim that all matches were lost from storage; the unresolved owner choice is whether `total` means all matches or returned items.

FastEmbed maps four names/aliases, probes dimension during construction, then serializes model access through `Arc<Mutex<_>>` inside `spawn_blocking`; initialization, poison, provider, and task-join errors are converted to `Result` errors (`fastembed.rs:20–31,52–88,91–145`). Its download-dependent tests are ignored. Hybrid search performs reciprocal-rank fusion over positions rather than source scores; duplicate IDs accumulate scores and source flags, while metadata is taken from the first occurrence (vector list processed first) (`hybrid.rs:66–124`). The probe delegates name/readiness/document-count; readiness inherits `VectorBackend::is_ready() == true`, and count errors become `None` (`probe.rs:30–64`; `backend.rs:34–52`). These are current APIs only, not readiness, model download, database, retrieval, or service execution evidence.

## Proposed findings (CC only; CDC review pending)

### FA-RS-046 — graph rkyv feature advertises persistence without a persistence path (Medium; CC-proposed)

- **Source and mismatch:** At source 719, graph Cargo gates `rkyv`, `memmap2`, and `blake3` as `graph-rkyv-cache` (`crates/fabryk-graph/Cargo.toml:15–20`). README says optional rkyv-based persistence (`README.md:10–17`); crate docs say the feature enables rkyv graph persistence (`src/lib.rs:1–10,64–77`). The complete feature-gated `rkyv_cache` module defines only byte-hash helpers (`src/persistence.rs:172–221`); public save/load are JSON (`:76–165`).
- **Current failure mode:** A caller enabling the advertised cache feature has no rkyv encode/save/load entrypoint in this crate; the public feature module supplies content hashes only. No compile or runtime result was observed.
- **Severity/confidence:** Medium; confidence high that the inspected complete crate source and feature/docs do not contain an rkyv persistence path. This is a public capability/documentation mismatch, not a claim that JSON persistence is broken.
- **Consumer and owner:** Consumers selecting `fabryk-graph`’s `graph-rkyv-cache` feature; logical owner is the graph crate/API maintainer, coordinating feature and package documentation.
- **Direction/compatibility:** Either implement the advertised binary persistence path with a separately defined format/version/error contract, or narrow the feature/docs/dependencies to the actual byte-hash helper. JSON APIs remain current. No implementation or policy is selected.
- **Future oracle:** After owner decision, inspect the feature’s public API and package docs; if persistence is promised, a separately authorized feature build and round-trip check should demonstrate encode/save/load and error handling. If the promise is removed, verify the published feature/docs name only the delivered helper. Not run.
- **Scale:** Crate/target API and feature/documentation contract; no application, workspace, package, or runtime acceptance.

### FA-RS-047 — graph cache can treat changed Markdown as fresh within one timestamp second (Medium; CC-proposed)

- **Source and current promise:** GraphBuilder describes cache freshness as comparing content hashes (`builder.rs:131–136,162–184`). Its complete helper instead collects `.md` relative paths and `mtime.as_secs()`, sorts them, and hashes those pairs (`:413–456`). The freshness reader compares only the stored key (`persistence.rs:148–165`). The cold build stores the key in GraphMetadata and the warm path returns before rediscovery (`builder.rs:162–185,285–302`).
- **Static valid case:** Reuse one cache path and one Markdown path; the file bytes change while its modification time remains in the same Unix second. The path+whole-second key remains unchanged, the metadata key matches, and the warm path returns the previous graph without parsing the changed bytes. This is manually derived, not executed.
- **Severity/confidence:** Medium because a changed source document can silently leave graph nodes/edges stale on a supported cache path; confidence high in the exact key and early-return branch. No prevalence or deployed result is claimed.
- **Contrary control:** The current cache miss test adds a new Markdown path (`builder.rs:735–762`); `skip_cache` forces a rebuild (`:764–787`). Those controls do not test same-path, same-second content changes.
- **Consumer and owner:** Callers reusing `GraphBuilder::with_cache_path`; logical owner is the fabryk-graph builder/persistence API owner.
- **Direction/compatibility:** Make freshness distinguish supported source content changes, or explicitly choose/document a weaker timestamp-based contract and its invalidation responsibility. Any format/key change must retain compatibility policy for existing JSON cache files. No repair is selected.
- **Future oracle:** Under an owner-approved key policy, build a cache, change bytes at an existing `.md` path without changing its whole-second mtime, and compare cold/skip-cache against warm results; keep unchanged-content, newly added-file and explicit `skip_cache` cases as controls. Not run.
- **Scale:** Function/module cache contract in the graph crate; manual-edge/extractor/builder-version dependence remains a separate ungraded caller-policy question, not folded into this finding.

### FA-RS-048 — vector `total` reports returned count while documented as matching count (Low; CC-proposed)

- **Source and contract:** `VectorSearchResults.total` is documented as “Total number of matching documents” (`crates/fabryk-vector/src/types.rs:259–270`). The simple backend truncates the filtered/sorted matches to `limit`, then sets `total = scored.len()` (`backend.rs:234–288`). LanceDB applies limit to the query (and to each bounded metadata-filter query), then sets `total = items.len()` (`lancedb.rs:113–160,251–292`).
- **Static valid case:** When more than `limit` documents satisfy a request, both implementations report the returned page length as `total`; source does not compute a pre-limit match count. This is code-path derivation, not a retrieval run.
- **Severity/confidence:** Low; high confidence in both implementations. The mismatch affects count interpretation; it does not show an index or result item was lost. No downstream pagination/client effect is claimed.
- **Consumer and owner:** Callers of `VectorBackend::search`; logical owner is the fabryk-vector result API and backend maintainers.
- **Direction/compatibility:** Decide whether the contract means all matching documents or only returned items. Then make both backend semantics or the field name/docs consistent, preserving threshold/category/metadata/limit behavior. No API change is selected.
- **Future oracle:** For a query with more matches than a small limit, verify both backends against the selected total definition while retaining zero-limit, empty-store, threshold, category, metadata conjunction and below-limit controls. Not run.
- **Scale:** Public result/API consistency across the in-memory and LanceDB backends; no runtime or actual client behavior was observed.

## Concrete contrary and negative checks

1. A graph with an orphan remains `valid` with an `ORPHAN_NODES` warning; warnings do not invalidate (`validation.rs:138–163,340–359`).
2. `RelatesTo` cycles are intentionally not prerequisite-cycle errors; only typed `Prerequisite` edges enter the cycle subgraph (`validation.rs:216–246,469–485`).
3. JSON graph loading skips edges with missing endpoints rather than failing the whole document (`persistence.rs:129–146,362–377`).
4. GraphBuilder records dangling extracted references and skips them; reverse-direction edges are distinct dedup keys and can both remain (`builder.rs:246–272`; source test `:599–624`).
5. A missing manual-edge file returns zero, dangling manual endpoints are recorded/skipped, explicit weight overrides relationship defaults, and legacy aliases remain in the parser (`builder.rs:338–410,525–543,642–702`).
6. An empty simple backend returns empty before calling its provider; `limit=0` truncates to empty. LanceDB with no indexed documents returns empty before embedding and does not create a table for an empty initial document list (`backend.rs:223–232,264–288`; `lancedb.rs:79–103,106–117`).
7. Simple cosine explicitly returns score 0 for unequal/empty/zero-norm vectors; this is a current fallback, not a claim that custom provider output is valid (`backend.rs:205–219`).
8. Lance metadata filters use conjunction across all provided pairs, category predicates escape quote characters, and bounded row-id batches still merge/sort/truncate globally (`lancedb.rs:127–153,172–292`). This is source reasoning; its tests were read, not run.
9. RRF handles vector-only, FTS-only, shared IDs, empty input and caller limit. It uses ranks and first-seen metadata (vector list before FTS), not source scores (`hybrid.rs:66–124,158–297`). No cross-backend score equivalence is imposed.
10. `create_vector_backend` returning Simple for disabled/unknown/Lance selection is explicitly documented in code as the current fallback; no feature-disabled parity or silent unsupported backend defect is inferred (`backend.rs:54–79,523–545`).
