## Aggregate: exact encoding and current admissibility

`AggregateConfig.group_by` is a required `Vec<String>` described as “Fields to group by”; aggregate operations and array collection have serde defaults (`aggregate.rs:18–49`). Public `from_params` deserializes that shape and returns the stage; its only explicit error is deserialization failure (`aggregate.rs:59–73`). No separator reservation, escaping, tuple framing, or field-value check appears in the complete stage implementation.

`Record` is a `serde_json::Map<String, Value>` whose documented values may be strings, numbers, booleans, arrays, or objects (`ecl-pipeline-topo/src/traits.rs:16–21`). For each `group_by` field, `compute_group_key` takes the literal `Value::as_str()` contents, substitutes the empty string for missing/non-string values, and joins the resulting string slices with a literal `|` (`aggregate.rs:75–82`). It does not use `Value::to_string()` and therefore does not quote/escape embedded string separators. On the all-present-string case below, the separator is accepted by the public deserialization shape and is not rejected by processing.

`process_batch` requires each supplied item to have a record, stores groups in a `BTreeMap<String, ...>` under that encoded key, and appends items with equal strings to the same group (`aggregate.rs:152–170`). It copies each configured group field from the first record, computes configured aggregates over every record in the group, and creates an output item whose ID includes the first input ID and encoded group key (`aggregate.rs:172–223`).

### Manual collision case

Use `group_by = ["left", "right"]` and `sum(amount) -> total` with two records:

| Input | left | right | amount | Encoded key |
| --- | --- | --- | ---: | --- |
| First | `AcmeA|AcmeB` | `AcmeC` | 1 | `AcmeA|AcmeB|AcmeC` |
| Second | `AcmeA` | `AcmeB|AcmeC` | 2 | `AcmeA|AcmeB|AcmeC` |

Both are valid string values for the public `Record` type and do not violate any inspected stage precondition. The derivation is therefore one map entry/group, with a sum of 3 rather than two groups with totals 1 and 2. The output group fields come from the first record; the second distinct tuple has no separate output. Its current generated ID has the form `<first-item-id>:agg:AcmeA|AcmeB|AcmeC` (`aggregate.rs:210–214`). This is a source-derived counterexample, not an observed execution.

### Aggregate controls and bounded exits

- Exact same tuple: equal encoded keys intentionally collect into one group; the composite-key test exercises separator-free field values (`aggregate.rs:480–529`).
- Distinct separator-free tuples: ordinary joined keys remain distinct when component boundaries cannot be confused by an embedded separator.
- One grouping field containing a literal `|`: the literal value is one component; with a single field there is no second tuple boundary to collide with.
- Explicit `group_by: []`: deserializes as an empty vector; the current helper joins zero components to the empty string, so all present-record inputs share that code-level key. This is recorded as a control, not a claim that global grouping is separately documented.
- Empty input: the group map stays empty and processing returns no outputs; the source test covers this (`aggregate.rs:556–566`).
- Missing `item.record` is an explicit permanent stage error (`aggregate.rs:162–167`). Missing/non-string group fields currently map to empty components; no separate numeric/missing-key contract is inferred here.

## Assemble: identities and repeated-stream question

`AssembleConfig` identifies `primary_stream`, `primary_key`, and a `Vec<AssembleJoin>`. Each join separately carries `stream`, primary-record `key`, secondary-record `foreign_key`, output alias `nest_as`, and `collect` (default false) (`assemble.rs:17–44`). `from_params` deserializes this configuration and has no additional uniqueness or cross-field validation (`assemble.rs:52–67`). The generic stage registry remains caller-configurable; caller-specific factories could add constraints, but no universal repeated-stream rule was found in the inspected current path.

| Identity | Current code role |
| --- | --- |
| Item `stream` | Partitions inputs; `primary_stream` selects primary items (`assemble.rs:97–107`). |
| `primary_key` | Reads a string from the primary record for generated output item ID/display name; it is distinct from join lookup keys (`:151–155,186–190`). |
| Join `key` | Reads the local string from the primary record for one join lookup (`:159–165`). |
| Join `foreign_key` | Reads string values from secondary records when that join's per-stream index is built (`:116–135`). |
| Join `stream` | Sole outer `join_indexes` key; a later definition for the same stream replaces the prior per-foreign-key index (`:118–136`). |
| `nest_as` | Output-record alias for that join result; the prescribed case uses distinct aliases (`:166–183`). |

### Prescribed repeated-stream manual candidate

The primary record has `id="AcmeT1"`, `buyer="B1"`, and `seller="S1"`. Its item stream is a distinct primary stream. Secondary item stream `parties` contains two records: row P has `buyer_code="B1"`, `seller_code="SX"`; row Q has `buyer_code="BX"`, `seller_code="S1"`. All lookup values are present strings. Define two joins to `parties`, one with local `key="buyer"`, `foreign_key="buyer_code"`, alias `buyer_info`; the other with local `key="seller"`, `foreign_key="seller_code"`, alias `seller_info`. Aliases are distinct, and neither join targets the primary stream.

| Definition order | Index for `parties` after construction | `buyer_info` lookup | `seller_info` lookup |
| --- | --- | --- | --- |
| Buyer definition, then seller definition | Seller-code index remains: `SX→P`, `S1→Q`; the second `insert("parties", index)` replaces the buyer-code index | Primary `B1` absent → `Null` in first-match mode | Primary `S1` → row Q |
| Seller definition, then buyer definition | Buyer-code index remains: `B1→P`, `BX→Q`; the second insertion replaces the seller-code index | Primary `B1` → row P | Primary `S1` absent → `Null` in first-match mode |

This is a manual derivation of the map construction and lookup if both definitions are admitted as supported configuration; it is not an observed assembled output. `Vec` deserialization accepts a sequence shape but is not by itself evidence that repeated-stream/different-foreign-key joins are part of the supported contract. Existing tests cover a single join and multiple joins over distinct streams (`assemble.rs:267–418`), not the repeated-stream combination. Retain the matter as **Q20-01**, not as a graded finding, until a current public promise or explicit owner decision establishes that this repetition is supported or forbidden.

### Assemble controls and bounded exits

- One join: current tests cover a primary/secondary match (`assemble.rs:267–308`).
- Multiple distinct streams: current tests use separate secondary streams (`assemble.rs:351–418`); their indexes do not overwrite one another.
- Same stream and same foreign key with distinct local keys/aliases: manual control; rebuilding from the same foreign-key field yields the same index data for both definitions, isolating the different-foreign-key mechanism.
- Matching and missing secondary values: current code nests the first matching record when `collect=false`; no match becomes `Null`. With `collect=true`, all matching records form an array and no match is an empty array (`assemble.rs:166–181`); source tests cover the missing-match forms (`:420–476`). “First match” is stated in the config comments and code, so no new ordering promise is added here.
- Missing primary stream: the selected primary list defaults to empty, so there are no output items (`assemble.rs:104–107`). A primary item without a record is a permanent stage error (`:140–149`).

## Proposed result and limits

One current aggregate composite-key collision is proposed as FA-RS-044 in the cumulative Rust report. It is bounded to the `AggregateStage` public configuration/implementation and its current string-key contract. Owner direction remains open: use an unambiguous tuple representation or make a separator restriction explicit and enforced. If key encoding changes, generated output IDs and downstream stable-identity compatibility must be considered. No repair or representation is selected.

Assemble's same-stream/different-foreign-key index overwrite remains Q20-01 because present evidence establishes the mechanism and deserializable shape but not supported repetition. Caller-specific registration constraints remain possible. This is not a new pipeline integration or project06 feature assignment.
