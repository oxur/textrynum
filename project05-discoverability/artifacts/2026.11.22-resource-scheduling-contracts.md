## Current promise and contrary scope evidence

`ResourceSpec.writes` is documented as exclusive access (`ecl-pipeline-spec/src/stage.rs:50–61`). The public `schedule::compute_schedule` docs promise that stages in one returned batch touch independent resources, and its algorithm says write-write conflicts must not share a batch (`ecl-pipeline-topo/src/schedule.rs:12–25`). The implementation accepts `_writers` but does not use it (`schedule.rs:30–35`); adjacency comes only from a resource that is both created and read (`schedule.rs:40–67`); batch assignment groups by derived depth (`schedule.rs:117–134`).

The contrary evidence remains material: `ResourceGraph` labels itself internal/model-only and says full usage begins in milestone 2.3 (`resource_graph.rs:12–18`). Yet current `resolve()` builds the graph, validates it, and places its computed schedule into `PipelineTopology` (`resolve.rs:93–115`); `PipelineTopology.schedule` is public and documents batches as concurrently runnable (`topo/src/lib.rs:40–68`); and the runner consumes that schedule. The public scheduler function is itself callable. The current artifacts therefore expose a present callable promise beside an explicit future/model-only scope comment. This review records the inconsistency without deciding whether the owner should reject the present contract or clarify/revise it.

## Downstream dispatch and enforcement boundary

`PipelineRunner::run` iterates schedule batches in order; `execute_batch` filters by the current condition hook, selects items by stream, then spawns one task per active stage in the batch (`runner.rs:147–170, 212–259, 398–427`). The condition hook currently returns true and documents expression evaluation as future work (`runner.rs:398–404`). `DefaultsSpec.concurrency` is described as the maximum concurrent operations within a batch and defaults to 4 (`spec/src/defaults.rs:5–33`), but runner passes this value to `execute_stage_items` separately for each non-batch stage. That helper creates a semaphore per invocation and holds each permit for one item task (`batch.rs:103–150`). Thus `concurrency=1` limits item work within each such stage executor; it does not serialize two stage tasks launched together, because their semaphores are separate. `execute_stage_batch` invokes `process_batch` without that semaphore (`runner.rs:251–258`, `batch.rs:183–234`). The `Stage` trait assigns transformation logic to handlers and orchestration/concurrency to the runner (`topo/src/traits.rs:216–259`).

The scoped search found no resource-keyed lock, gate, or additional resource-derived dependency in the assigned resolver/runner/batch path. This supports a statement about the inspected source path, not every downstream handler or external resource implementation. A schedule containing A and B does not prove their handler effects overlap: handlers may ignore declarations, serialize internally, receive no items, or be subject to caller policy. No actual write, stage timing, or overlap was observed. Planner output-contract mismatch, runner-permitted task concurrency, and unobserved effects remain distinct claims.

## FA-RS-043 — Same-depth exclusive writers remain in one promised conflict-free batch (Medium; CC-proposed)

- **Source and current promise:** At source `719c58f245fe4a9115c7c0391d3e268c99157e2f`, `ecl-pipeline-spec/src/stage.rs:50–61` defines `writes` as exclusive access; `ecl-pipeline-topo/src/schedule.rs:12–25` promises independent resources/no write-write conflict within each returned batch. `schedule.rs:30–35, 40–71, 117–134` accepts but ignores the writer map for conflict handling and groups by creator-reader depth. `resource_graph.rs:44–80, 191–198` confirms duplicate writes are collected rather than rejected. Current consumption is reachable through `resolve.rs:93–115`, public `topo/src/lib.rs:40–68`, and `runner.rs:147–170, 212–259`.
- **Severity rationale:** Medium. A valid configuration that declares two exclusive writes to the same resource receives a schedule that places them together despite the public scheduler’s no-conflict promise. The runner is permitted to dispatch same-batch stages concurrently; resulting data effects depend on handlers/callers and were not observed. The mismatch can undermine caller reliance on the declared schedule contract, but this static evidence does not establish a production race or data loss.
- **Confidence:** High that the source-level manual declarations are accepted and produce one same-depth batch; no runtime reproduction was performed.
- **Contrary evidence and scope:** `ResourceGraph` calls itself internal/model-only and places full use in future milestone 2.3 (`resource_graph.rs:12–18`). Preserve this tension; it may support owner clarification or rejection of the present promise. Project06 feature work remains held and the original agent-workflow framework remains cancelled. This finding does not commission resource-aware scheduler implementation.
- **Affected consumer and logical owner:** Callers of public `ecl_pipeline_topo::schedule::compute_schedule`, `resolve()`/`PipelineTopology.schedule` consumers, and the topo/spec API maintainers responsible for keeping declaration and schedule promises coherent. Runner consumers are affected only insofar as they rely on the computed batch contract.
- **Fix direction and compatibility decision:** Owner chooses a coherent contract: honor exclusive same-resource writes in scheduler grouping, or explicitly narrow/revise the current declaration and scheduler promise to the implemented dependency model (and decide whether such declarations should be rejected). No API shape, ordering policy, or repair is selected here. Enforcing exclusion can change batch composition and throughput; narrowing/rejecting declarations changes which callers may rely on the existing wording. Keep a deliberate handler/caller serialization policy as a distinct possible control, not an implied scheduler guarantee.
- **Future discriminating oracle:** After an explicit owner decision and separate authorization, use the valid A/B shared-writer case above and assert the selected contract at `compute_schedule`/`resolve` output. If exclusivity is retained, A and B must not appear in the same batch; if the promise is narrowed or declarations rejected, assert that exact policy. Include the C→A/B, shared-read, distinct-write, single-stage, and manually serialized controls. A separate behavioral check would be required to establish actual handler overlap/effects.
