## Current promise and contrary scope evidence

`ResourceSpec.writes` is documented as exclusive access (`ecl-pipeline-spec/src/stage.rs:50–61`). The public `schedule::compute_schedule` docs promise that stages in one returned batch touch independent resources, and its algorithm says write-write conflicts must not share a batch (`ecl-pipeline-topo/src/schedule.rs:12–25`). The implementation accepts `_writers` but does not use it (`schedule.rs:30–35`); adjacency comes only from a resource that is both created and read (`schedule.rs:40–67`); batch assignment groups by derived depth (`schedule.rs:117–134`).

The contrary evidence remains material: `ResourceGraph` marks the type internal, says it is currently used in tests, and puts full usage in milestone 2.3 when `resolve()` is implemented (`resource_graph.rs:12–18`). Yet current `resolve()` builds the graph, validates it, and places its computed schedule into `PipelineTopology` (`resolve.rs:93–115`); `PipelineTopology.schedule` is public and documents batches as concurrently runnable (`topo/src/lib.rs:40–68`); and the runner consumes that schedule. The public scheduler function is itself callable. The current artifacts therefore expose a present callable promise beside an explicit future/model-only scope comment. This review records the inconsistency without deciding whether the owner should reject the present contract or clarify/revise it.

## Downstream dispatch and enforcement boundary

`PipelineRunner::run` iterates schedule batches in order; `execute_batch` filters by the current condition hook, selects items by stream, then spawns one task per active stage in the batch (`runner.rs:147–170, 212–259, 398–427`). The condition hook currently returns true and documents expression evaluation as future work (`runner.rs:398–404`). `DefaultsSpec.concurrency` is described as the maximum concurrent operations within a batch and defaults to 4 (`spec/src/defaults.rs:5–33`), but runner passes this value to `execute_stage_items` separately for each non-batch stage. That helper creates a semaphore per invocation and holds each permit for one item task (`batch.rs:103–150`). Thus `concurrency=1` limits item work within each such stage executor; it does not serialize two stage tasks launched together, because their semaphores are separate. `execute_stage_batch` invokes `process_batch` without that semaphore (`runner.rs:251–258`, `batch.rs:183–234`). The `Stage` trait assigns transformation logic to handlers and orchestration/concurrency to the runner (`topo/src/traits.rs:216–259`).

The scoped search found no resource-keyed lock, gate, or additional resource-derived dependency in the assigned resolver/runner/batch path. This supports a statement about the inspected source path, not every downstream handler or external resource implementation. A schedule containing A and B does not prove their handler effects overlap: handlers may ignore declarations, serialize internally, receive no items, or be subject to caller policy. No actual write, stage timing, or overlap was observed. Planner output-contract mismatch, runner-permitted task concurrency, and unobserved effects remain distinct claims.
