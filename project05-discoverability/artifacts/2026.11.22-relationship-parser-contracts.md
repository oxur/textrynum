## Canonical Relationship and parser map

`Relationship` derives `PartialEq` and has 11 built-in variants plus `Custom(String)` (`types.rs:36–73`). Built-in `.name()` values are canonical lowercase names; the derived serde enum accepts the listed lowercase aliases while retaining the enum's variant identifiers as its normal serialized names (`types.rs:36–73,98–113`). `FromStr` documents PascalCase/snake_case and case-insensitive built-in matching, and returns `Custom(original_string)` for unrecognized input (`types.rs:136–159`). It lowercases and removes underscores before matching.

The manual parser lowercases before its match. Its accepted legacy aliases `prereq`, `related`, and `answers_questions` are not canonical `FromStr` spellings; they are preserved as existing behavior. The MCP parser lowercases input, handles seven built-ins, and turns every other string into a lowercase `Custom`. By contrast, canonical `FromStr` preserves the exact original spelling for unknown custom names. Because equality is typed and exact, a built-in name represented as `Custom("contrasts_with")` is not equal to `ContrastsWith`; equal-looking strings do not erase the enum-variant distinction.

## Producer, storage, and consumer contract

The public `ConceptCardGraphExtractor` documents its frontmatter-to-Relationship map and maps `contrasts_with` to `Relationship::ContrastsWith` (`concept_card_extractor.rs:62–76,147–175,203–222`). Its source tests include a `contrasts_with` frontmatter case and expect a `ContrastsWith` edge (`:500–542`). `GraphData::add_edge` requires both endpoint nodes to exist and stores the supplied typed `Edge` unchanged; it does not normalize relationship names (`types.rs:471–489`). `EdgeInfo::from` serializes the edge's `.name()` (`query.rs:45–66`), so this stock edge is exposed as the string `contrasts_with`.

Both `RelatedArgs.relationship` and `NeighborhoodArgs.relationship` are optional strings described as relationship-type filters (`tools.rs:88–124`). The related schema calls it a relationship-type filter with examples `prerequisite` and `relates_to`; the neighborhood schema also describes a relationship-type filter (`:360–443`). Both handlers pass the parsed private `Relationship` value to the same `neighborhood` function; `graph_related` uses radius 1 and `graph_neighborhood` defaults to radius 1 (`:664–694,765–804`). The algorithm compares that filter with the stored edge's typed enum using `PartialEq` (`algorithms.rs:132–203`). No downstream normalization changes the parsed value or stored edge before that comparison.

## Manual-edge boundary and owner questions

`ManualEdge.relationship` is a public `String` described only as a “Relationship type name”; its builder accepts an optional JSON file (`builder.rs:42–53,119–123`). The parser maps nine built-ins and aliases. For `same_as` and `cites`, it currently returns `Custom("same_as")` / `Custom("cites")`; when weight is absent, those custom variants use `0.5`, while typed `SameAs` and `Cites` use `0.9` and `0.7` (`builder.rs:339–353,392–403`; `types.rs:81–95`). An explicit manual weight overrides the selected variant default (`builder.rs:392–395`). The existing manual-edge test uses `relates_to` with an explicit weight; parser tests cover selected aliases and a custom string, not `SameAs` or `Cites` (`builder.rs:525–543,642–660`). README/docs and inspected public comments do not enumerate an exhaustive ManualEdge relationship set. Therefore no claim is made that the loader promises all 11 built-ins, and no `SameAs`/`Cites` finding is proposed.

Relevant exits and controls: a missing manual-edge file returns zero; dangling endpoints are recorded and skipped before parsing; the manual dedup key uses the raw input string; a fresh-cache hit returns before manual-edge loading; and explicit weights bypass defaults (`builder.rs:162–185,356–410,662–702,708–733`). These boundaries do not establish deployed weights or outputs. `GraphData::add_edge` itself does not deduplicate (`types.rs:471–489`). Existing serialized `Edge`/`Relationship` values retain typed/custom variants (`types.rs:36–73,340–379`); no persisted corpus was inspected.

**Q21-01 — ungraded manual built-in subset question.** Does the public ManualEdge string contract intend `same_as` and `cites` to construct their typed built-ins, or are they intentionally accepted as custom relationship identifiers? An owner decision should name the supported set and whether an omitted weight follows the canonical built-in or custom default. A future behavioral oracle should follow that decision, include explicit-weight and exact-alias controls, and retain missing-file, dangling-endpoint, dedup, and cache-hit boundaries. No policy or repair is chosen here.

**Q21-02 — ungraded custom-name casing question.** Should unknown custom relationship names preserve case or normalize it across `FromStr`, manual loading, and MCP filtering? Today `FromStr` preserves original spelling while both private parser fallbacks lowercase, and typed equality is case-sensitive. A future oracle should follow an explicit owner choice and account for serialized/cache compatibility; it should preserve the existing manual aliases and the distinction between custom tags and typed built-ins. No global case policy or migration is selected.
