## Current public wording and implementation

The exact `shortest_path` comment says: “Uses petgraph's A* algorithm with uniform cost.” (`algorithms.rs:213–216`). `Relationship::default_weight` documents weights as influencing pathfinding (`types.rs:76–95`), and `Edge.weight` likewise says it influences pathfinding (`types.rs:340–352`). These statements do not say all edges have equal cost, do not define weights as distance rather than strength, and do not promise minimum hop count. The phrase “uniform cost” names a weighted shortest-path method; petgraph documents that its A* `edge_cost` supplies edge costs, zero heuristic behaves like Dijkstra, and the estimate must be admissible (`petgraph-0.8.3/src/algo/astar.rs:13–42`). No equal-cost/unit-edge or minimum-hop defect is inferred from wording alone.

The current route implementation calls A* with integer edge cost `(1.0 / e.weight().weight.max(0.01)) as u32` and a zero heuristic (`algorithms.rs:237–243`). Once A* returns node indices, the code maps nodes and reconstructs each `Edge` by `graph.graph.find_edge(from,to)`, then sums those returned raw `Edge.weight` values into `PathResult.total_weight` (`algorithms.rs:245–267`). Thus the optimizer's integer accumulated cost and the result's raw-weight sum are distinct values with different meanings. The public field docs call the latter “Total path weight” (`algorithms.rs:41–52`), but do not define its domain interpretation or tie it to the A* score.

`GraphData` is a directed petgraph `DiGraph`; public `add_edge` requires both endpoint IDs already exist, then inserts the edge into both the graph and flat edge list (`types.rs:385–490`). Petgraph explicitly permits parallel edges and inserts a new outgoing edge at the adjacency head (`graph_impl/mod.rs:625–680`). Its directed `find_edge(a,b)` scans that outgoing adjacency list and returns the first edge whose target is `b` (`graph_impl/mod.rs:1058–1085`). `PathTracker` stores predecessor nodes, not predecessor edge IDs (`astar.rs:163–197`).

For the parallel case, if the 1.0 edge is inserted first and the 0.5 edge second, petgraph's new-head insertion means endpoint `find_edge` returns the 0.5 edge; reverse insertion returns the 1.0 edge. This is an insertion-order-sensitive representative edge for a node sequence whose A* cost is 1. The public `PathResult.edges` says “Edges along the path”; both parallel edges connect those path nodes. Without a stronger contract, it is not established that the returned edge must be the optimizer-selected edge, nor that the result is invalid. The resulting `total_weight` is the raw sum of returned representative edges.

## MCP projection, supported follow-up, and early exits

The `graph_path` schema takes `from` and `to` only and describes the operation as “Find the shortest path between two nodes” (`tools.rs:385–402`). On success the handler emits `found`, a node path whose steps carry `relationship_to_next`, node-count `length`, and `total_weight`; it does not emit edge IDs, edge origins, or the internal A* cost (`tools.rs:697–737`; `query.rs:97–119`). A separate `graph_get_node_edges` tool accepts a node and direction and returns incident edges with endpoints, relationship name, and raw weight (`tools.rs:500–531,883–893`; `query.rs:45–67,240–345`). This can expose candidate edges, including parallel alternatives, but it does not identify which edge was used for a prior path result. Omission of internal cost or edge IDs is not by itself a defect; the current consumer contract does not promise those fields.

The source-level early exits are bounded as follows (`algorithms.rs:216–272`): unknown start or target returns `PathResult::not_found`; same-node returns a found one-node path with no edges and weight 0; a directed graph with no route returns not-found after A*. In MCP, invalid argument deserialization is an invalid-params error; a found result takes the success projection above, and not-found returns `found:false` plus a message (`tools.rs:697–737`). Existing tests around `algorithms.rs:797–840` cover found, not found, same-node, and missing endpoints; they were read only.

## Questions retained; no finding proposed

1. Which domain meaning should `shortest_path` optimize: reciprocal relationship-strength cost, raw edge-weight sum, hop count, or another metric? Existing wording and implementation support weighted optimization and show the current calculation, but do not establish the intended semantic interpretation. No canonical metric is selected here.
2. For parallel edges, is `PathResult.edges`/MCP `relationship_to_next` intended to be any representative edge joining consecutive path nodes, or the exact edge selected by the optimizer? Current public docs do not state selected-edge provenance. Endpoint lookup makes the representative insertion-order-sensitive. No guarantee is invented.
3. Is public `total_weight` intentionally the sum of returned raw relationship weights, as current code computes, or should the public contract expose/describe optimizer cost separately? The implementation is clear; intended consumer semantics remain unspecified.
4. What tie behavior, if any, should callers rely on for equal-cost parallel edges/routes? No stable tie-selection promise was found in the assigned units.

These remain questions because no promise sufficient to classify a defect was established. They do not alter accepted slice14 finding FA-RS-038 about prerequisite edge orientation; that is a separate contract axis. Zero new findings is a valid outcome for this slice.
