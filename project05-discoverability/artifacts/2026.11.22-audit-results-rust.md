## Confirmed findings

### FA-RS-001 — Filesystem-backed MCP lookup accepts parent traversal IDs

- **Severity:** Medium
- **Source:** `crates/fabryk-core/src/util/files.rs:71-85`; consumer chain `crates/fabryk-mcp-content/src/fs_content_provider.rs:216-224`, `fs_guide_provider.rs:167-176`, and registry dispatch `tools.rs:335-340,730-738`.
- **Later repair owner:** `fabryk-core::util::files` owns the shared path-resolution boundary; affected traced consumers are `fabryk-mcp-content`'s filesystem item/guide providers and content/guide tool registry dispatch. Later MCP source-provider raw joins remain assigned to their full pass and are not claimed covered here.
- **Scale:** line/function, logical unit, crate/target, application/service.
- **Observed failure:** explicit lookup substitutes caller-provided `id` into `{id}.md` and joins it to the configured root, then accepts any existing path without containment or file-type checks. The real content and guide provider methods returned `../outside.md` sibling fixture content. `ContentTools::call("get", {"id":"../outside"})` and `GuideTools::call("get_guide", {"id":"../outside-guide"})` also returned those contents as successful MCP tool results. The path was outside each configured directory. A directory named `folder.md` passed lookup and failed only when `read_file` attempted to read it.
- **Evidence strength:** reproduced through provider and tool-registry entrypoints against isolated temporary fixtures. No MCP wire/client or network server was exercised; no claim is made about a deployed unauthenticated exploit. Deployment exposure depends on tool registration and host authorization.
- **Fix direction:** validate identifiers as a single safe logical ID; canonicalize/contain the resolved target within the configured root and require a regular file before returning it. Preserve documented pattern support with positive tests.
- **Compatibility-sensitive decisions:** nested identifiers/pattern overrides may be intentional; determine and document allowed ID grammar before tightening.
- **Validation oracle:** traversal, absolute path, symlink escape, sibling fixture, directory named `.md`, nested valid pattern and ordinary missing ID through both provider methods and registry dispatch; assert no outside bytes are returned.

### FA-RS-002 — Infrastructure authentication errors are returned as client 401s

- **Severity:** Medium
- **Source:** `crates/fabryk-auth/src/middleware.rs:116-129`; classifier `crates/fabryk-auth/src/error.rs:43-57`.
- **Later repair owner:** `fabryk-auth::AuthLayer` owns validator-error classification; affected consumers are callers composing that layer with `TokenValidator` implementations, including the Google validator and host applications.
- **Scale:** line/function, logical unit, crate/target, application/service.
- **Observed failure:** middleware maps every validator error to `unauthorized_response`, without consulting `AuthError::is_client_error`. The classifier explicitly identifies `JwksFetchError` as non-client/server-side. An actual `AuthLayer` oneshot with `Err(JwksFetchError("fixture upstream timeout"))` returned 401 and included `failed to fetch JWKS: fixture upstream timeout` in the JSON body. The inner service was not called. Invalid credentials also returned 401 as expected; a valid user reached the inner service and returned 200.
- **Evidence strength:** actual Tower service entrypoint with deterministic validator; source classifier and response code align with the observation.
- **Fix direction:** distinguish credential rejection from validation-provider failure and choose an availability/server response for the latter; return a stable client-safe message and retain details only in protected logs.
- **Compatibility-sensitive decisions:** decide status/retry behavior for `NoMatchingKey` during key rotation separately from transport/parse failures; preserve client-error 401 behavior.
- **Validation oracle:** oneshot valid, invalid signature, missing/empty token, JWKS transport failure and malformed JWKS; assert status, body redaction, challenge and inner call count.

### FA-RS-003 — Every unknown Google `kid` can cause another JWKS fetch

- **Severity:** Medium
- **Source:** `crates/fabryk-auth-google/src/lib.rs:226-250,253-277`.
- **Later repair owner:** `fabryk-auth-google::GoogleTokenValidator` owns JWKS cache-miss/refresh policy; affected consumers are `fabryk-auth::TokenValidator`/`AuthLayer` callers and host applications using Google validation.
- **Scale:** line/function, logical unit, crate/target, application/service, workspace/system.
- **Observed failure:** each cache miss calls `refresh_keys`; a successful response with no matching `kid` leaves a fresh cache but no negative result. A subsequent token with the same unknown `kid` misses again and performs another fetch. Concurrent misses can also pass the lookup before any fetch result is installed. CDC's independent local-only fixture observed sequential requests for the same unknown `kid` return `NoMatchingKey` with request counts 1 then 2; concurrent behavior remains unmeasured.
- **Evidence strength:** source control flow plus CDC's independently executed local fixture. The initial author-side fixture attempt exited 101 with `PermissionDenied (Operation not permitted)` at socket bind; that failure remains historical and is not replaced by the later independent replay. No provider request occurred.
- **Fix direction:** coordinate refreshes and apply a bounded unknown-key refresh policy (for example, short negative caching or refresh cooldown) while retaining a deliberate key-rotation path.
- **Compatibility-sensitive decisions:** unknown-key retry latency versus prompt recognition of provider key rotation.
- **Validation oracle:** local JWKS fixture counts requests for sequential and concurrent unknown kids, cached known kid, expired cache and a changed key set; bound all fixture waits.

### FA-RS-004 — Google JWKS and userinfo requests have no client deadline

- **Severity:** Medium
- **Source:** `crates/fabryk-auth-google/src/lib.rs:72-80,162-177,253-265`.
- **Later repair owner:** `fabryk-auth-google::GoogleTokenValidator` owns the async HTTP client and both JWKS/userinfo request boundaries; affected consumers are the same Google `TokenValidator`/`AuthLayer` callers.
- **Scale:** line/function, logical unit, crate/target, application/service, workspace/system.
- **Observed failure:** `GoogleTokenValidator::new` constructs `reqwest::Client::new`; neither JWKS nor userinfo request sets a request/client timeout. The locked dependency is reqwest 0.13.5; its async `ClientBuilder::timeout` documentation states the default is no timeout. CDC's bounded local-only replay observed one accepted stalled JWKS request and validation still pending at a 500 ms outer guard, then cancelled; that does not establish an internal deadline or infinite runtime.
- **Evidence strength:** source plus exact-version primary dependency documentation and CDC's bounded local observation. No external call occurred; the outer guard is not evidence of an internal timeout.
- **Fix direction:** configure finite connect and total/read deadlines for provider requests and classify deadline expiry as infrastructure failure.
- **Compatibility-sensitive decisions:** values should account for key rotation and expected provider latency; use an outer test bound only as a test safety guard, not as proof of an internal timeout.
- **Validation oracle:** a local server that accepts and stalls; assert validation returns at the configured deadline with a provider-side error and valid configured-audience ID-token fixtures still complete. Opaque-token behavior must follow the explicit compatibility disposition in FA-RS-009.

### FA-RS-005 — A panicking initializer strands service state at Starting

- **Severity:** Medium
- **Source:** `crates/fabryk-core/src/service.rs:102-143,299-343`.
- **Later repair owner:** `fabryk-core::ServiceHandle`/initializer supervision owns the lifecycle transition; affected consumers include readiness waiters and orchestration callers, with broader application assembly assigned to its later pass.
- **Scale:** line/function, logical unit, crate/target, application/service.
- **Observed failure:** if `init_fn` panics, `spawn_with_retry` exits through the task `JoinError` without setting `Failed`. After awaiting the returned `JoinHandle`, the handle remained `Starting`; `wait_ready(5ms)` timed out instead of observing a terminal failure. By contrast, a successful retry reached `Ready` after two attempts and exhausted `Err` attempts reached `Failed`. `max_attempts=0` performs no initialization and leaves `Stopped`; recorded as a configuration boundary, not a separate finding.
- **Evidence strength:** actual public lifecycle API; the expected panic was caught as a JoinError and recorded in the raw log.
- **Fix direction:** supervise initializer panics/aborts and transition to a terminal state, or explicitly make the join result the sole failure signal and update `wait_ready`/docs so observers cannot mistake `Starting` for live progress.
- **Compatibility-sensitive decisions:** whether task cancellation is a failure, shutdown, or caller-owned state transition.
- **Validation oracle:** panic, explicit abort, cancellation during backoff, zero attempts, retry success, exhausted errors and waiter behavior after each terminal condition.

### FA-RS-006 — ADC resolver accepts a directory as the credential file

- **Severity:** Low
- **Source:** `crates/fabryk-gcp/src/adc.rs:45-80`.
- **Later repair owner:** `fabryk-gcp::adc` owns candidate selection and file-type validation; affected consumers are callers of the public ADC path resolver, with complete application wiring reserved for the later application-assembly pass.
- **Scale:** line/function, logical unit, crate/target, application/service.
- **Observed failure:** docs and return type describe a credential *file*, but each candidate is accepted with `Path::exists`. In an isolated subprocess, `GOOGLE_APPLICATION_CREDENTIALS` pointing to a directory was returned as the resolved ADC path. That blocks fallback to a valid home candidate, and a later `read_credential_type` cannot parse the directory.
- **Evidence strength:** actual public resolver in a child process with a task-specific temporary HOME and directory; missing override correctly fell through to the owned macOS-home fixture.
- **Fix direction:** require a regular file (and decide how symlinks are treated) before selecting an override or fallback candidate; continue to the next valid candidate otherwise.
- **Compatibility-sensitive decisions:** symlinked credential files are common and may need to remain supported.
- **Validation oracle:** file, directory, dangling symlink, unreadable file, empty/nonexistent override and valid fallback in isolated child processes; never read ambient credential contents.

### FA-RS-007 — MockRedis converts an invalid counter to zero on increment

- **Severity:** Medium
- **Source:** `crates/fabryk-redis/src/mock.rs:49-54`; production counterpart `client.rs:44-51` and trait `lib.rs:36-40`.
- **Later repair owner:** `fabryk-redis::MockRedis::incr_by` owns mock behavior; the `RedisOps` contract owner must reconcile it with `RedisClient`/Redis `INCRBY`. Affected consumers are tests and callers substituting the mock for the production implementation.
- **Scale:** line/function, logical unit, crate/target, workspace/system.
- **Observed failure:** mock `incr_by` uses `.parse().ok().unwrap_or(0)`, so a stored `not-a-number` becomes `Ok(1)`. Production uses Redis `INCRBY`, which reports an error for stored values that cannot be represented as an integer. Official Redis docs describe that error and limit the operation to signed 64-bit integers. No Redis server is installed here, so the production command was not runtime-probed.
- **Evidence strength:** mock entrypoint reproduction plus exact `RedisOps` production command and primary Redis protocol documentation; production-server behavior remains static/documented only.
- **Fix direction:** make MockRedis return `RedisError` on invalid, signed/overflow-invalid values consistently with the documented production command semantics; add parity cases.
- **Compatibility-sensitive decisions:** `RedisOps::incr_by` uses `u64` while Redis counters are signed 64-bit. Define supported range/overflow behavior before changing either path.
- **Validation oracle:** same invalid/current/missing/negative/overflow matrix against MockRedis and disposable loopback Redis when available; compare returned values and error categories.

### FA-RS-008 — MockRedis does not implement the trait's glob pattern semantics

- **Severity:** Low
- **Source:** `crates/fabryk-redis/src/mock.rs:67-76`; trait promise `crates/fabryk-redis/src/lib.rs:42-44`; production uses `SCAN MATCH` at `client.rs:67-83`.
- **Later repair owner:** `fabryk-redis::MockRedis::scan_keys` and the `RedisOps` pattern contract own parity; affected consumers are tests and callers substituting the mock for the production implementation.
- **Scale:** line/function, logical unit, crate/target, workspace/system.
- **Observed failure:** mock strips trailing `*` and performs `starts_with`; it does not implement other Redis glob metacharacters. With key `ab1`, mock `scan_keys("a?*")` returned an empty list. The trait promises glob-pattern matching; Redis SCAN MATCH uses glob-style patterns. No production server was available, so that side is confirmed by source and official docs, not a live comparison.
- **Evidence strength:** actual MockRedis entrypoint and source contract; production semantics from Redis documentation.
- **Fix direction:** implement the supported Redis glob grammar in the mock or narrow and document the trait contract so tests cannot silently assert behavior production does not provide.
- **Compatibility-sensitive decisions:** whether a dependency-free mock uses a glob library and which Redis pattern forms are supported.
- **Validation oracle:** wildcard, single-character, character-class, escaped metacharacter and literal-key cases against both mock and Redis SCAN MATCH.

### FA-RS-009 — Opaque Google access-token validation does not enforce configured audience

- **Severity:** Medium
- **Source:** `crates/fabryk-auth/src/lib.rs:18-26`; `crates/fabryk-auth-google/src/lib.rs:56-63,99-110,129-143,162-205,281-290`.
- **Scale:** line/function, logical unit, crate/target, application/service.
- **Observed failure:** the public `AuthConfig.audience` is documented as the expected audience and `TokenValidator::validate` passes it into `validate_token`. The JWT branch applies it with `Validation::set_audience`; the non-JWT branch calls `validate_access_token(token, domain)` and drops it. That branch accepts userinfo identity fields (`sub`, `email`, `email_verified`, `hd`); `UserInfoResponse` has no audience field. Thus an opaque token accepted by Google's userinfo endpoint can produce an authenticated user without this validator comparing the token to the configured application audience. This is a static contract finding, not a claim that a particular live token or provider path was exercised.
- **Evidence strength:** source-level complete-flow comparison plus Google's backend guidance: it directs backend authentication to verify ID tokens and compare their `aud` with the application's client IDs; Google's OpenID Connect documentation separately describes access tokens as a way to obtain profile information. No Google token, credential, provider request, or runtime exploit was used.
- **Later repair owner:** `fabryk-auth-google::GoogleTokenValidator` owns the opaque-versus-JWT authentication boundary, coordinated with the `fabryk-auth::AuthConfig.audience` contract; affected consumers are `TokenValidator`/`AuthLayer` callers and host applications configuring Google authentication.
- **Fix direction:** unless the owning contract explicitly narrows `audience` to ID tokens, reject opaque access tokens for authentication and require an audience-validated ID token. Do not add a new authentication platform or assume userinfo response supplies client binding.
- **Compatibility-sensitive decisions:** this changes the existing opaque-token fallback for callers relying on access-token authentication. Confirm whether that fallback is supported product behavior; if it is, define and verify a trustworthy client-binding signal before retaining it.
- **Validation oracle:** through the public validator, a valid configured-audience ID token succeeds and wrong/missing audience fails; opaque input is rejected without accepting userinfo identity when no trustworthy audience signal exists. If the opaque path is intentionally retained, a local fake userinfo response alone cannot prove client audience binding and must not be treated as passing that oracle.

### FA-RS-010 — Bearer authentication scheme parsing is case-sensitive

- **Severity:** Low
- **Source:** `crates/fabryk-auth/src/middleware.rs:135-141`.
- **Scale:** line/function, logical unit, crate/target, application/service.
- **Observed failure:** `extract_bearer_token` uses case-sensitive `strip_prefix("Bearer ")`. The author probe and CDC's independent `AuthLayer` replay both observed canonical `Bearer <valid-token>` reaching the inner service with 200, while lowercase `bearer <same-token>` returned 401 without reaching it. RFC 9110 §11.1 defines the authentication-scheme token as case-insensitive, so the implementation rejects a valid protocol spelling. This is an interoperability denial, not an authentication bypass.
- **Evidence strength:** actual `AuthLayer` oneshot observation is in the author run and independent CDC replay; protocol requirement is RFC 9110 §11.1. No new runtime run was needed for this correction.
- **Later repair owner:** `fabryk-auth::extract_bearer_token`/`AuthLayer` owns scheme parsing; affected consumers are services using that middleware.
- **Fix direction:** compare only the scheme token case-insensitively while preserving the credential bytes exactly; retain rejection of absent, empty, malformed, and non-Bearer credentials.
- **Compatibility-sensitive decisions:** none for conforming clients; malformed whitespace/token parsing must remain bounded and explicit.
- **Validation oracle:** canonical, lowercase, and mixed-case scheme spellings with the exact same valid token all reach the validator unchanged; empty token, missing separator, wrong scheme, and invalid token remain rejected and never reach the inner service.

## Policy-sensitive hypothesis (not counted)

### H-RS-001 — Google domain fallback may not enforce Workspace membership

`GoogleTokenValidator::check_domain` falls back to the email suffix whenever the signed ID token has no `hd` claim (`crates/fabryk-auth-google/src/lib.rs:145-154,208-224`); the unit test `test_check_domain_fallback_from_email` explicitly preserves that policy. Google says that a domain restriction for Workspace/Cloud organization membership must check `hd`; absent `hd` means the account is not in a Google-hosted domain, and a verified third-party email can have changed ownership. See [Google OpenID Connect claim guidance](https://developers.google.com/identity/openid-connect/openid-connect) and [Google backend authentication guidance](https://developers.google.com/identity/sign-in/web/backend-auth). This is not counted as confirmed because `AuthConfig.domain` is documented as an allowed email domain, which could intentionally mean email-suffix matching. The security owner must decide whether this setting represents Workspace membership or any verified email suffix. If the former, require matching `hd`; validate a signed matching-email JWT with no `hd` as rejected. No JWT with absent `hd` was run through the public validator; no case-specific runtime result is claimed.

### H-RS-002 — Bearer challenge may be unusable when no resource URL environment variable is set

`unauthorized_response` builds the `resource_metadata` value from `KASU_RESOURCE_URL`, then `TAPROOT_RESOURCE_URL`, and defaults to the empty string (`crates/fabryk-auth/src/middleware.rs:152-168`). With neither variable set, the actual challenge was `Bearer resource_metadata="/.well-known/oauth-protected-resource"`. RFC 9728 §5.1 describes this parameter as the protected-resource metadata URL and shows an HTTPS URL. This remains a hypothesis because deployments may require one of those variables and no real MCP client was exercised. Decide whether generic `AuthConfig` should carry an explicit resource URL and validate against intended client behavior before grading.

## Correctness and limits retained

- `AuthError::is_client_error` correctly identifies `JwksFetchError` as non-client; the defect is middleware not using the distinction. Disabled auth mode intentionally passes through, as its unit test confirms.
- JWT path checks signature algorithm, audience, issuer, expiry, verified email, and configured domain; opaque-token path verifies userinfo response and uses the same domain helper but does not apply configured audience (FA-RS-009). Google documents audience checking for ID-token backend authentication; that does not establish audience validation on the opaque path. No actual Google token or external network request was used.
- `/mcp` authorization metadata intentionally uses Google-specific values in the source. Protected-resource routes both preserve configured Acme resource/authorization-server values in the oneshot probe.
- `BackendSlot::require` documents that the caller must store the backend before setting Ready. Search fallback additionally checks the inner Option. That precondition was not treated as a framework guarantee violation.
- `AppState`'s unsafe Send/Sync implementations match its `ConfigProvider: Send + Sync` bound and Arc-only field; compile-time positive trait checks pass. No unsoundness claim supported.
- ACL has no implemented policy logic and is documented as a placeholder. This is deferred scope, not an incomplete implementation finding.
- Redis production service parity remains unrun; `redis-server` was absent. No Google provider endpoint was contacted. The initial author-side local JWKS listener setup failed with `Operation not permitted`; the independent CDC replay later used an owned loopback fixture for unknown-kid and bounded-stall observations, cited in [CDC evidence](2026.11.22-core-auth-cdc-evidence.md). Those local results do not establish live-provider behavior.
- Only default features were built. The seven slice02 package manifests declare no direct features. No workspace all-feature/native/CI gate was repeated; accepted arc00 evidence remains historical at its original source and date.

## Primary references for refinement dispositions

- Google [backend ID-token verification](https://developers.google.com/identity/sign-in/web/backend-auth) requires checking the ID token's `aud` against the application's client IDs. Google [OpenID Connect guidance](https://developers.google.com/identity/openid-connect/openid-connect) describes access tokens as a way to obtain profile information.
