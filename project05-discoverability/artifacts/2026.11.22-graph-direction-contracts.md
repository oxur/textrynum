## Source-derived direction contract

The type-level statement is that A must be understood before B
(types.rs:37–40). For an edge whose from/to endpoints follow that statement,
A -> B means A is prerequisite of B. The relationship type itself has no
orientation field beyond Edge.from and Edge.to (types.rs:340–353).

The source-card producer follows a different convention: a current card B with
listed prerequisite A emits B -> A (concept_card_extractor.rs:203–208). The
mock extractor does the same (extractor.rs:210–216). GraphBuilder phase2 inserts
the returned edges without swapping endpoints (builder.rs:241–273); GraphData
stores from -> to as supplied (types.rs:471–489). Manual JSON edges also retain
the supplied from/to through load_manual_edges and GraphData insertion
(builder.rs:356–410). JSON persistence serializes Edge values and reconstructs
the same endpoint direction (persistence.rs:76–94,109–145).

Query boundaries:

| Public query | Actual direction/operation | Consequence under semantic A -> B edges |
| --- | --- | --- |
| GraphData::prerequisites(id) | Direct outgoing Prerequisite neighbors via get_related (algorithms.rs:657–667) | Returns B for A; this is the dependent side, not A’s prerequisites. |
| GraphData::dependents(id) | Direct incoming Prerequisite neighbors (algorithms.rs:669–678) | Returns A for B; this is the prerequisite side. |
| prerequisites_sorted(target) | Recursively follows incoming Prerequisite edges, then filters a full-graph topological order (algorithms.rs:274–338) | Returns prerequisite ancestors of target and orders them topologically. |
| free dependents(id, max_depth) | BFS over incoming Prerequisite edges, depth capped at MAX_BFS_DEPTH, excludes start (algorithms.rs:415–457) | Walks prerequisite ancestors, not downstream dependents. |
| learning_path(target) | Wraps prerequisites_sorted; numbers its ordered items and appends target (algorithms.rs:565–602) | Inherits recursive prerequisite direction and ordering. |
| get_related(id, relationships, direction) | Outgoing selects edge target; Incoming selects edge source (algorithms.rs:460–491) | Neighbor mapping is correct for the supplied Direction. The issue is which direction callers choose for the named contract. |

The three MCP routes delegate without reorienting:
graph_prerequisites calls prerequisites_sorted (tools.rs:740–762);
graph_dependents calls free dependents (895–918); graph_learning_path calls
learning_path (1001–1021). GraphTools defaults node_filter to None
(tools.rs:258–267); optional filtering is post-processing. Custom names map
slot names and dispatch to the same handlers (:280–303,664–695), so neither
default filtering nor custom naming explains or repairs direction semantics.
The fabryk-graph facade exports the graph types and queries; the
fabryk-mcp-graph facade exports GraphTools and its argument types
(fabryk-graph/src/lib.rs:31–48,65–69;
fabryk-mcp-graph/src/lib.rs:38–46).

## Manual single-edge and three-node derivation

These are source-level derivations from branch conditions and graph direction
calls, not an executable model, a Rust run, or client observation. Set membership
is kept separate from ordering. GraphData convenience helpers return direct
neighbors only; prerequisites_sorted is recursive and topologically ordered;
free dependents is depth-limited BFS; learning_path uses that recursive order
and appends the target.

### Single relationship: A is prerequisite of B

| Representation/convention | Edge stored | Query and source-followed direction | Manual result | Contract reading |
| --- | --- | --- | --- | --- |
| Type semantic convention | A -> B | GraphData::prerequisites(A), Outgoing | {B} | Opposite side from the name under this convention; expected direct prereqs of A: {}. |
| Type semantic convention | A -> B | GraphData::dependents(B), Incoming | {A} | Opposite side from the name; expected direct dependents of B: {}. |
| Type semantic convention | A -> B | prerequisites_sorted(B), reverse BFS over Incoming | {A}; order [A] | Matches prerequisites of B. |
| Type semantic convention | A -> B | free dependents(A), Incoming, depth >= 1 | {} | Misses B; expected dependents include B. |
| Card-list convention | B lists A, therefore B -> A | GraphData::prerequisites(B), Outgoing | {A} | Matches card-listed direct prerequisite. |
| Card-list convention | B lists A, therefore B -> A | GraphData::dependents(A), Incoming | {B} | Matches card-derived dependent. |
| Card-list convention | B lists A, therefore B -> A | free dependents(A), Incoming, depth >= 1 | {B} | Matches card-derived dependent. |
| Card-list convention | B lists A, therefore B -> A | prerequisites_sorted(B), Incoming | {} | Misses A; expected prerequisites include A. |
| Card-list convention | B lists A, therefore B -> A | learning_path(B) | [B] | Omits listed A; expected [A,B] if that list is the input contract. |

For a single edge, learning_path has target as its sole step when
prerequisites_sorted returns an empty set; when it returns A, it appends B.
MCP outputs inherit the corresponding graph query result.

### Acyclic chain: A prerequisite of B; B prerequisite of C

| Input convention | Stored edges | GraphData direct prerequisites(C) | prerequisites_sorted(C): set and order | free dependents(A), depth >= 2 | learning_path(C) |
| --- | --- | --- | --- | --- | --- |
| Semantic edge direction | A -> B; B -> C | {} (only immediate outgoing neighbors of C) | {A,B}; topological order [A,B] | {} because A has no incoming prerequisite edge | [A,B,C] |
| Card lists prerequisites | B -> A; C -> B | {B} (the immediate item listed by C) | {} because C has no incoming edge | {B,C}, BFS layers B then C | [C] |

The tables expose two distinct questions without choosing an answer: the
producer’s card-list direction conflicts with the Relationship description,
and the direct helper/free-dependent orientation differs from the recursive
prerequisite/learning-path orientation. A single canonical-direction decision
must reconcile them. It cannot be inferred from one passing historical test.

## Concrete negative checks

1. get_related maps Direction::Outgoing to edge target and Incoming to edge
   source correctly (algorithms.rs:473–486); do not file it as a direction bug.
2. GraphData::add_edge verifies both endpoints exist and stores the supplied
   edge unchanged (types.rs:471–489); no hidden normalization occurs there.
3. Manual edges preserve caller-provided from/to values and mark origin Manual
   (builder.rs:356–410); compatibility cannot assume only extractor edges.
4. JSON save/load carries Edge values and rebuilds the same from/to arc
   (persistence.rs:76–94,109–145). GraphMetadata includes generic builder_version
   (:37–60); no prerequisite-orientation-specific marker/transformation is
   shown in this range. No absence of all version metadata is claimed.
5. prerequisites_sorted returns an empty prerequisite list when a present
   target has no traversed edges (algorithms.rs:302–308), and reports a missing
   target before traversal (:278–285).
6. free dependents rejects a missing node, returns no traversal for depth zero,
   caps requested depth at ten, and excludes the start node (algorithms.rs:423–457).
7. learning_path always appends the target after the prerequisite result
   (algorithms.rs:569–602); ordering symptom is inherited rather than a second root.
8. GraphTools starts with no node filter; filters are optional list-result
   post-processing, and custom names are slot aliases (tools.rs:258–303).
9. graph_prerequisites, graph_dependents and graph_learning_path delegate to
   the named algorithms; MCP does not add endpoint reversal (tools.rs:740–762,
   895–918,1001–1021).
10. The source includes tests on both sides of the convention; their presence
    does not show which tests were executed or prove external-client behavior.
11. Both recursive traversal loops select only Prerequisite relationships
    (algorithms.rs:293,446). RelatesTo/LeadsTo edges in the shared fixture are
    ignored, as the unrun assertion1044–1052 documents; these are not a cause
    of the direction difference in the all-Prerequisite acyclic controls.

## Open decisions for the repair owner and CDC

- Which persisted edge meaning becomes canonical: from is prerequisite-of to,
  or from is the card/current dependent and to is its listed prerequisite?
  This assignment does not choose.
- Which stored/manual JSON compatibility policy follows that decision: explicit
  orientation-specific version marker, migration, compatibility reader, or a separately approved
  transition? Existing endpoints are carried through load/save; blind reversal
  is not proposed.
- Should APIs expose immediate versus recursive prerequisites consistently and
  name depth/order semantics explicitly? This is a design question; this review
  does not add a second finding.
- Does the repair oracle need extractor-produced, hand-authored, and previously
  persisted edge examples across direct, recursive, learning-path, and MCP
  entrypoints? Proposed oracle includes all these inputs to prevent a local fix
  from leaving another route on the former convention.
